# Unity 2D：直接修改 JPEG 编码的故障效果

这个示例直接修改 JPG 的压缩数据。处理过程中不先解码成 RGB 来画条带；修改结果写成 JPG 后，再由 Unity 解码并显示。

## 文件与使用步骤

- `JpegGlitch.cs`：独立的 C# JPEG 压缩数据处理代码，没有 Unity 依赖。
- `JpegGlitchSprite.cs`：Unity 的 SpriteRenderer 组件。
- `sample-original.jpg.bytes`：可直接拖进 Unity 的测试输入，内容仍然是原始 JPG 二进制。
- `sample-original.jpg`、`sample-coefficients.jpg`：测试原图和修改 JPEG 系数后的输出。
- `sample-byte-damage.jpg`：随机修改两个字节的输出。能否显示、如何补全损坏区域取决于解码器。
- `comparison.png`：原图与系数修改结果的对照展示，仅用于查看。

1. 将两个 `.cs` 文件复制到 Unity 项目的 `Assets` 下。
2. 使用附带的 `sample-original.jpg.bytes`，或把自己的基线 JPG **复制**成 `photo.jpg.bytes` 后导入 Unity。只改副本扩展名，不用文本编辑器另存。
3. 在一个 GameObject 上添加 `SpriteRenderer` 和 `JpegGlitchSprite`，把 `.jpg.bytes` 拖到 `Jpeg Bytes` 字段。
4. 选 `Coefficients`，进入 Play Mode。确保相机对准这个物体，缩放能容纳图片。
5. 运行时修改参数后，在组件右键菜单选择 `Generate JPEG Glitch`；选择 `Next Seed` 生成另一组条带。
6. 选择 `Save Current Modified JPG`，会把已显示图片对应的修改后 JPG 字节保存到 `Application.persistentDataPath` 下，控制台会给出路径。保存时不会再做一次 `EncodeToJPG`。

## 两种模式

### Coefficients：控制彩色断带与黑白模糊边缘

流程：

```
原始 JPG 字节
→ 解析 JPEG 标记、量化表和 Huffman 表
→ 把扫描数据解码到量化后的 DCT 系数
→ 按 MCU 区域修改系数
→ 重新进行 DC 差分、游程与 Huffman 编码，写回 JPG
→ Unity LoadImage → SpriteRenderer
```

这里没有进行 RGB 像素编辑，也没有额外的图像后处理。

- **彩色条带**：对选中的块增加 Cb、Cr 的 DC 系数偏移，让这些块产生不同的色偏；少量修改 Y 的 DC 值改变亮度。
- **不完整、断续的条带**：每条带只占一段图像宽度，并按随机种子留下缺口。
- **黑白模糊边缘**：在条带上下方的相邻 MCU 中，将色度系数清零，保留少量亮度低频 AC 系数，删除其余 AC 系数，并提高亮度对比。结果是局部灰度、细节损失以及模糊的明暗边界。

这是一个具体的效果设计。条带上下方是示例选择的处理区域，不是自动识别照片中物体轮廓；没有参考图时，不能保证与某一次记事本损坏的结果完全相同。

| 参数 | 建议起点 | 作用 |
|---|---:|---|
| Seed | 37 | 控制本实现中的随机布局；在同一运行环境中可重复生成 |
| Bands | 4–8 | 条带数量 |
| Min / Max Band Rows | 1 / 2 | 条带厚度，以 MCU 行数计 |
| Gap Probability | 0.15–0.35 | 越高，条带缺口通常越多 |
| Color Shift | 40–90 | 色偏幅度 |
| Brightness Shift | 10–25 | 条带亮度偏移 |
| Gray Edge Rows | 1 | 上下灰度边缘宽度；0 关闭 |
| Edge Keep Ac | 3–8 | 保留的亮度 AC 项数量；越小，细节越少；0 仅保留块均值 |
| Edge Contrast | 1.3–2.0 | 灰度边缘的明暗对比 |

JPEG 的单个 DCT 块为 8×8 个分量样本。常见 4:2:0 图像中，一个 MCU 对应 16×16 个亮度像素；4:2:2 对应 16×8，4:4:4 对应 8×8。因此，本示例的条带边界按 MCU 对齐。它不是任意像素精度的遮罩。

核心调用：

```csharp
byte[] originalJpg = jpegBytes.bytes;
byte[] changedJpg = JpegGlitch.EditCoefficients(
    originalJpg,
    new JpegGlitch.Settings {
        seed = 37,
        bands = 6,
        colorShift = 65,
        grayEdgeRows = 1,
        edgeKeepAc = 5
    });

var texture = new Texture2D(2, 2, TextureFormat.RGB24, false);
bool loaded = ImageConversion.LoadImage(texture, changedJpg, false);
// 在 loaded 为 true 时创建 Sprite；完整组件已包含失败处理与资源释放。
```

### RawByteDamage：记事本式的不可预测损坏

它在 SOS 头之后、EOI 之前选择少量熵编码数据字节，翻转其中的位。代码保留结构标记、FF00 字节填充以及已有的重启标记，但这**不能保证熵编码仍然有效**。

从 `Byte Edits = 1–3` 开始。`Byte Start` 和 `Byte Span` 指的是扫描数据里的字节区间，**不对应图像中的准确高度或位置**。每次生成都以原始 JPG 为输入，不累计破坏。

随机改动可能改变系数、导致解码失步、出现断带，也可能使大量区域失去内容，甚至让 Unity 拒绝读取。组件会在加载失败时保留此前的 Sprite。返回成功也不代表图像局部或整体符合预期。

记事本看到的乱码是二进制数据经过字符编码解释的结果。不要使用 `TextAsset.text`、`ReadAllText` 或 `Encoding.UTF8.GetString` 再写回；字符替换、换行转换等会扩大损坏范围。应一直使用 `byte[]`。

## 限制与集成建议

- 支持 8 位基线 Huffman JPEG、单次扫描；彩色输入需为 YCbCr，分量 ID 按 1/2/3 排列，采样为 4:4:4、4:2:2 或 4:2:0。也支持 ID 为 1、采样 1×1 的灰度图。
- 不支持渐进式、多扫描顺序 JPEG、RGB JPEG、CMYK/YCCK、算术编码等。解析器会明确拒绝。输入尺寸上限设为 1600 万像素。
- 遇到不支持的输入，可从原图另存为标准/基线 JPEG，关闭渐进式选项，再复制为 `.jpg.bytes`。灰度输入本身没有色度分量，不能产生彩色色偏。
- 系数模式保持原来的量化表，使用简单但合法的完整 Huffman 表重新写入扫描数据。因此输出文件可能更大；这不是体积优化器。
- 效果来自输出 JPG 中的系数变化。再次改变 Unity 的纹理压缩设置不会代替这些变化。`Bilinear` 只控制显示时的采样，模糊主要由示例对亮度系数的修改产生。
- 每次 `Generate` 都读取和重写压缩数据并上传纹理。动画可在加载阶段预生成有限数量的结果并缓存，或以较低频率更换；不要默认在 `Update()` 中逐帧生成大图。性能需要在目标设备测量。
- 原始随机损坏文件在不同解码器、Unity 版本和平台上可能有不同表现。需要稳定呈现时，优先用系数模式。
- 若未来需要更广的 JPEG 支持或更高性能，可用 libjpeg-turbo 的系数读写接口编写 Unity 原生插件；它能访问量化后的 DCT 系数。本示例不依赖原生插件。

## 已完成的验证

核心 C# 代码已用本地 C# 编译器编译。使用独立 JPEG 解码器检查了 21 个基线输入，包含三种采样、优化 Huffman 表、非整块尺寸、1×1 图片、灰度、重启标记和高质量噪声图。

验证包括：未开启效果的系数重写与原图解码像素完全一致；效果结果能解码；固定参数在本测试环境中输出一致；修改后的 JPEG 可再次进行保持系数的重写；原始字节损坏保留文件长度并避开所保护的字节；渐进式、CMYK 和截断输入正确报错。

附带的图片来自合成测试图。没有在本机实际启动 Unity 编辑器验证组件，也没有测试目标移动设备；核心测试不等于 Unity 全平台验证。
