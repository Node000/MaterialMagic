# 二层地图系统实现方案（架构审阅稿）

> 状态：提案，未实施。依据：本轮用户提供的 brainstorm，以及当前二层原型、一层关卡/存档代码。
> 目标：先建立人类可读、以对象为主、可持续扩展的地图实现模板与内容规约；本轮不实现具体房间，不修改场景、Prefab、美术参数或现行玩法。
> 文中的“建议”不等于已确认玩法；未定问题集中在第 14 节。本方案不默认沿用原型的地图尺寸、数量、内容配额或 Boss 揭示方式。
> 代码级细化见 [二层地图系统代码架构](二层地图系统代码架构.md)：字段、方法、战斗接点与快照契约以该详细提案为参考；本页保留产品整理与总体方向。
> 基于联网资料、资产调查和原型初始运行的 [现状调研与改造实施案](二层地图现状调研与改造实施案.md) 规定具体复用方式、风险、分批顺序和验证边界；三稿均为未实施提案。

## 1. 设计摘要

推荐把二层设计为：**有领域归属的条带探索地图，其中地点和沿途可交互物都是具有身份与状态的对象。**

- **领域 Region** 决定大范围氛围、敌人分布、精英势力和前往其他领域的条件。
- **条带 Strip** 决定有序的探索节奏、走向、交叉连接和终端地点。
- **格位 Cell** 提供空间位置与对象摆放位置，不承担所有玩法。
- **地图对象 MapObject** 表达敌人、陷阱、NPC、侧壁恢复物、线索及终端地点，各自保存状态、处理自己的规则。
- **探索会话 ExplorationSession** 接收玩家行动，按固定顺序调用对象，并控制战斗/事件等外部流程的往返。
- **表现 View** 只呈现上述状态；摄像机、地面、墙面、小地图不是规则来源。

不使用“所有格子只有一个 LevelType + 一堆布尔字段”的方案，也不为每一种外观建一个行为类。**相同规则换资源用配置；新规则才增加明确命名的类。**

## 2. 脑暴内容整理与约束来源

### 2.1 本轮明确提出的方向

| 方向 | 归入的系统能力 |
| --- | --- |
| 地图由条带组合，每条带对应一个序列 | 条带有序格位与序列模板 |
| 普通怪→事件→精英→奖励；也可能含转向格 | 序列槽位、空间转向/连接、对象摆放 |
| 条带终端为奖励格 | 条带终端保留奖励格要求；不以 Boss、商店或休息格替代 |
| 献祭、roll、三选一；Boss、商店、休息 | 献祭/roll/三选一按奖励内容继续设计；已确认 Boss、商店、休息是各自独立的格子，不归类为奖励格 |
| 道中恢复物在侧壁 | 有朝向/侧壁锚点、可独立交互的地图对象 |
| 经过陷阱受伤或负面；用对应箭头剪除 | 仅保留候选类型记录；具体效果、用牌与解除规则暂不实现 |
| 事件、NPC、线索 | 可交互对象与任务事实，不强制一律进入战斗面板 |
| 敌人在前一格触发战斗，提前可见 | 敌人模型位置、可见性、接敌触发位置必须分开 |
| 部分敌人在若干回合后恢复 | 行动时钟与对象恢复状态，不使用真实时间倒计时 |
| 区域围绕精英展开，至少击败或成功邀请一个精英才能去下一区域 | 已确认邀请精英也满足通行条件；击败与邀请保留不同结果事实 |
| 领域位置决定氛围与敌人，条状地形决定组件装饰 | 领域语义、空间结构、表现配置分离 |

### 2.2 世界观与长线目标

二层是南极黑墙内的囚笼，Kaari 击破外壳后潜入，部分强大负面 AI 已逃出，多数仍留在内部。这里的 AI 实体存在不被人类认可；其时间观念与“运动/行动”相关。敌人因各自理由阻挡 Kaari，交战中存在邀请同行或击败的分支。

原始记录写“完成三件事”，但实际列出四项，应在任务结构中保留四项，不擅自合并：

1. 找到方舟：方舟是能带其他 AI 离开的方式，不限定为某艘船，由某个精英拥有。
2. 说服其他 AI 前往方舟。
3. 打开由守备 AI 管辖的洪水通路，可战斗或通过其他方式达成。
4. 驾驶/启动方舟，带 AI 逃离并释放。

工程上用具名目标状态与 AI 关系状态承载，而不是把“击败 Boss”直接等同于二层通关。“除了 ta 和 ta”指代不明，保留为叙事待定，不据此编码排除名单。

## 3. 当前实现与复用边界

### 3.1 已有两条原型路径

- PC 四分区地图：`Assets/Scripts/SecondFloor/SecondFloorPCMapGenerator.cs` 输出 `RunMapGridModel`；当前配置每区 12×11、6 条带、总范围 25×23。它是固定四分区轮廓，不是新的领域系统。
- 独立条带地牢：`Assets/Scripts/SecondFloor/StripDungeonMapGenerator.cs`、`StripDungeonMap.cs`、`StripDungeonMapConfig.cs`；当前配置 18×14、6～8 条带，生成环路、端点普通内容与隐藏 Boss。
- 第一人称展示：`Assets/Scripts/SecondFloor/SecondFloorStripDungeonFirstPersonPrototype.cs`，目前处理移动、地形、主题、界面和揭示，没有接入房间玩法。

新方案与两者都不是原样等价：原型只是“端点放普通内容”，不是“每条带终端奖励”；原型是“随机条带主题”，不是“按领域控制敌人和氛围”。原型中的隐藏 Boss 及双路径约束可复用为可选生成校验，但不是本轮脑暴确认的硬规则。

### 3.2 不直接继承的耦合

- `RunMapCellModel` 目前以单个 `LevelData` 和布尔标记表达格子，无法清晰表达同格陷阱、侧壁物与敌人的独立状态。
- `RunManager.MoveMapPlayer` 先进入目标格；`HandSystemUI.ChapterMapMoveRoutine` 随后消耗格子内容并开关卡，不符合前一格接敌与可恢复敌人。
- `HandSystemUI.FinishBattleRoutine`、`FinishReward` 承担奖励、自动商店、旧地图推进和 Boss 通关。二层不能完整套用这些结束流程。
- `RunSaveSystem.SaveCurrentRun` 依赖旧 mapNodes，地图快照仅存旧格子字段；新对象图不应塞进这些字段，更不能只存一个 seed。

### 3.3 推荐迁移策略

1. 首先复制现有第一人称二层场景为 `Assets/Scenes/2层制作测试.unity`，后续实际地图实现持续在此副本迭代。源场景、旧一层和原型保留，不删除、不改GUID；场景复制不等于隔离共享脚本/Prefab/SO。
2. 先用 `PrototypeLayoutAdapter` 将现有条带输出转换为新对象图，显式核对坐标/邻接，包括旧相邻通行产生的接触边；新运行态不引用旧可变模型。通过后再提取纯布局阶段，另接领域和序列，不复制旧内容规则。
3. 复用 `PlayerState`、敌人模型、`BattleManager`、事件/奖励展示的现有能力，但先建立具名、窄接口的往返边界。
4. `HandSystemUI` 只做必要接线和旧实现适配；不得继续承载二层门禁、对象恢复、领域任务等业务。
5. 接口无法安全包裹时，做最小局部抽取并验证一层回归；不借本任务全量重写战斗/UI。
6. 保留连续地形段、交叉格共享及现有主题资源，提取 GeometryPlan 和绑定；先核查 Scribble 重复初始化与网格规模，再做需视觉审批的密度/分段优化。Boss局部揭示不重建全图。

## 4. 对象模型与所有权

以下名称是建议契约名称，不是当前项目中已经存在的类。

```text
SecondFloorSession                         本局二层入口和流程协调
├─ DungeonMap                              地图结构和对象注册表
│  ├─ DungeonRegion[]                     领域、条带引用、出口/精英引用
│  ├─ DungeonStrip[]                      有序格位、终端地点引用
│  ├─ DungeonCell[]                       位置、领域归属、摆放槽位
│  ├─ DungeonConnection[]                 显式可通行边与门禁引用
│  └─ MapObject[]                         敌人/陷阱/地点/NPC等实例
├─ ExplorerState                           格位、朝向、已发现信息
├─ ExplorationProgress                     行动计数、发现与永久精英事实
├─ JourneyProgress（后续）                  正式任务阶段才加入，不预建空方舟字段
└─ PendingInteraction                      跨战斗/事件/奖励的未完成请求
```

### 4.1 核心职责表

| 对象 | 负责 | 不负责 |
| --- | --- | --- |
| `DungeonMap` | 按 ID/位置查询唯一对象、结构校验、显式邻接关系 | UI、自动开战、直接发奖 |
| `DungeonRegion` | 领域身份、主题/敌人池引用、精英与出口、当前通过状态 | 决定所有房间的具体行为 |
| `DungeonStrip` | 格位顺序、序列槽位映射、起终端、连接锚点 | 用显示顺序代替实际可走邻接 |
| `DungeonCell` | 整数坐标、唯一领域归属、对象摆放槽位 | 单一 LevelType 包办所有规则 |
| `DungeonConnection` | from/to、方向、是否双向、边界门禁 | 靠墙模型是否存在判断可走性 |
| `MapObject` | 实例身份、定义引用、生命周期、摆放与具体规则 | Input、Camera、Scene 查找、全局运行结束 |
| `SecondFloorSession` | 接收行动、校验、顺序调度、外部流程往返、提交结果 | 按每个地点 ID 写 switch |
| `JourneyProgress` | 具名任务目标与关系结果，判断最终离开条件 | 到处散落字符串标记或代替所有对象状态 |
| `DungeonWorldView` / `DungeonMinimapView` | 根据快照和变更刷新显示 | 修改生命、解锁门、重新随机内容 |

### 4.2 一个对象只由一个地方拥有

- 地图注册表拥有全部领域、条带、格位、连接和地图对象；运行对象之间持有同一实例的只读引用，存档转换为稳定 ID，不各复制一份可变实例。
- 交叉点是**一个格位**，可被多个条带引用；不因为属于两条条带而复制对象或重复触发。
- 每个格位只归属一个领域。领域交界用边界连接/过渡格明确表示，不能按“先遍历到哪个条带”决定环境主题。
- 条带默认属于一个领域；跨领域行程拆成两条带，通过边界连接相接，避免一条带承担两套敌人池和门禁。
- 摆放槽位采用 `Ground`、`Occupant`、`Destination`、`Wall`，墙面另存绝对朝向；同槽冲突在生成时拒绝。不用随玩家朝向变化的“左墙/右墙”作为持久身份。
- 每个对象有稳定 `ObjectId` 和 `DefinitionId`；同一种敌人/地点可有多个实例，互不共享已领取、已击败状态。
- 跨对象关联在运行态使用统一实例引用，持久化使用稳定 ID；Unity 场景引用只绑定表现，不能充当存档身份。

## 5. 以对象为主，但不做继承迷宫

### 5.1 三层分离

| 层 | 例子 | 生命周期与规约 |
| --- | --- | --- |
| Definition：不可变配置 | `RegionDefinition`、`StripSequenceDefinition`、`EnemyMapObjectDefinition`、现有 `StripDungeonThemeDefinition` | ScriptableObject；Inspector 绑定资源；运行中不写回 SO |
| Model：本局对象 | `DungeonRegion`、`DungeonStrip`、`EnemyMapObject`、`TrapMapObject` | 普通 C# 类；维护本局状态；不依赖场景对象 |
| View：显示组件 | `MapObjectView`、`EnemyMapObjectView`、`RegionEnvironmentView` | MonoBehaviour；绑定 Model ID，按状态刷新和播放动画，不判定规则 |

允许模型使用明确的坐标/方向值类型；“不依赖场景”不要求为摆脱 `Vector2Int` 而立即引入一整套数学库。

### 5.2 最小继承与能力组合

建议保留薄基类 `MapObject`。第一批只建立证明模板需要的遭遇与通用交互测试对象，例如 `EnemyMapObject` 和测试用 `DestinationMapObject`。陷阱、恢复物、NPC/线索及具体房间先保留类型记录，进入对应里程碑后才增加行为类，不为每个候选房间提前建空类。

能力接口只解决确实不同的触发方式：

- `IApproachTrigger`：玩家到接敌位置后的触发。
- `IEnterTrigger`：玩家真正进入格位后的触发。
- `IMapInteractable`：玩家显式选择交互的通用入口，模板阶段用测试对象验证；侧壁拾取或陷阱解除等具体用途以后再接。
- `IExplorationTickListener`：少数需要探索行动推进的对象。

对象可以实现一个或多个能力，不要求所有对象重写一组空的 virtual 方法。一个敌人需要恢复时可持有普通 `RespawnSchedule` 对象；不扩成 `RespawningRegionEliteEnemyWithQuest...` 多层继承。

首批用具体 `RegionGate` 表达“指定领域至少一个精英被击败或成功邀请”；出现第二种真实门禁需求时再抽象条件接口，不预建 All/Any 或通用脚本语言。

### 5.3 可读性规则

- 一文件一个主要职责类；文件名与类型名一致；二层新代码建议使用 `MaterialMagic.SecondFloor` 命名空间。
- 方法使用业务动词：`TryMove`、`CanCross`、`BeginEncounter`、`ApplyOutcome`、`ScheduleRespawn`，不使用难以追踪的 `ExecuteEverything`。
- 状态改动通过具名方法完成，集合对外只读。避免任意脚本直接改 `isCompleted`。
- 规则调用链必须可直接跳转：输入→Session→对象→结果→Session。事件用于通知显示/音效，不用全局事件总线串联核心规则。
- 接口只放在变化边界：战斗、存档、表现等；稳定的小型内部类不必一类一接口。不引入 DI 容器、ECS 或反射式行为注册。
- 地图对象创建入口集中且显式。可以有一个按定义子类创建对象的小型工厂；新增类型必须同步创建与存档映射，不把 switch 散布在生成器、UI 和存档各处。
- 普通差异用配置，例如回血量、模型、音效、敌人组；改变行为流程才建新类型。
- 注释说明规则原因、时点、所有权；不重复翻译每行代码。

## 6. 条带序列、空间拓扑与领域门禁

### 6.1 序列不是坐标数组的另一个名字

`StripSequenceDefinition` 描述逻辑节奏，布局阶段才把槽位映射到条带中的格位：

```text
普通敌人 → 事件/线索 → [转向/连接锚点] → 精英 → 终端奖励地点
```

- 槽位定义语义、先后顺序、允许留白距离、对象摆放要求；不在模板里写具体场景路径。
- 一个逻辑槽位可占多个行走格；不是每走一步都要有内容。
- 详细设计首版沿用直线条带：在交叉处转向即进入另一条带，不引入“折弯逻辑条带”对象。若未来明确需要跨拐角的同一内容序列，再增加路线编排能力，不混淆空间条带与内容顺序。
- 每条条带指定规范起端与终端。序列描述的是规范方向下的布局，不默认玩家无法倒着走，也不默认必须按顺序解决全部内容。
- 奖励格、Boss 格、商店格、休息格是独立玩法类型。条带终端按奖励格约束生成，不把后三者塞进奖励类型池；后三者的具体位置与接入方式另由布局规则确定，不据此假定它们必须在终端。献祭/roll/三选一可作为奖励格的候选内容继续讨论。
- “逻辑条带”只是提案中对“被当作同一个有序探索单元的格位序列”的称呼，不是已确认的新玩法对象。它是否跨越拐角尚未定案；不能因本提案术语直接改变现有直线条带规则。
- 交叉点上的共享对象只有一个，必须显式引用；默认把专属内容放在非共享格，避免一场战斗同时被两条序列统计两次。
- 转向在首版作为空间连接与输入动作表达，不先做独立的“转向奖励房”。若未来转向格有额外规则，再增加对应对象。

### 6.2 显式连接，而非“坐标挨着就能走”

可走性由 `DungeonConnection` 决定。两条走廊几何贴近、跨领域隔一面墙时，不能因为曼哈顿距离为 1 就自动互通。格位坐标服务于绘制和查找，连接边才是规则权威。

### 6.3 领域门禁

建议用**领域连接图 + 领域内部条带图**两级结构。领域数、形状、是否四分区都由配置指定，不固化为旧原型的四个象限。

门禁绑定在领域出口连接上，读取指定领域精英对象的永久事实。例如：

```text
连接：梦泡领域 → 下一领域
条件：梦泡领域中至少一个计入门禁的精英对象曾被击败或成功邀请
```

- 必须对所有出境边统一校验；只锁一个视觉门，其他交叉条带仍可绕过，不算实现了门禁。
- 满足条件所需的精英必须在锁内可达，不允许“要过门才能接触开门精英”。
- 已确认：击败或成功邀请指定精英都能满足通行条件；两种结果分别记录，不把邀请伪装为击败。
- 精英恢复不撤销已经满足门禁的历史事实，不反复关门（建议）。
- 隐藏/发现、可通过、已交互是三个不同概念。门已显示不等于可通行，敌人可见不等于立即开战。

### 6.4 生成流水线

固定阶段、明确中间输出，失败返回阶段与原因：

1. 构建领域连接图，分配精英势力和关键目标的候选领域。
2. 在领域内生成条带布局与显式连接。
3. 将序列槽位映射到格位，并保留终端位置。
4. 放置精英、普通敌人、事件、侧壁物与陷阱；处理占位冲突和触发距离。
5. 解析本局具体内容 ID/敌人组，生成稳定对象 ID，分配领域主题与表现变体。
6. 校验拓扑、门禁可解性、端点、关键目标可达性，产出完整地图快照。

失败重试有上限，不静默删除精英/门禁/目标来“凑一张能生成的图”。可复用原型算法，但新校验不能只检查物理连通。

## 7. 行动、接敌与流程往返契约

### 7.1 唯一行动入口

已确认探索采用伪 3D 地牢操作：点击屏幕中间向当前朝向前进一格，点击左侧原地左转，点击右侧原地右转；移动不依赖箭头牌。现有第一人称原型以屏幕横向三等分处理这些操作，可作为输入参考，具体点击区域布局仍由表现层配置。

输入层提交 `MoveForward`、`TurnLeft`、`TurnRight`；后续确需对象交互时再增加 `Interact(objectId)`。鼠标/触屏调用同一入口，核心规则不读 `Input`。当前不增加 `UseArrow` 命令、探索手牌或探索抽弃牌循环。

详细设计将业务阶段收敛为 `Exploring / AwaitingEncounter / Ended`；解析和应用结果在同步方法内完成，不单独保存中间阶段。只有 Exploring 接收行动，演出忙碌由场景控制器单独门控。失败结果包含具体原因，例如墙、门禁未满足、忙碌、目标已消失，而不是一个含义不明的 false。

### 7.2 一次移动的确定顺序（建议）

1. 校验会话状态、输入、目标连接、门禁与占位；不合法则返回原因，不改状态、不计行动。
2. 计算本次行动会进入的格位以及接敌对象；按固定优先级/稳定 ID 排序，检测同一位置多敌冲突。
3. 提交移动到合法落点。
4. 调用当前已实现的落点进入能力；玩家死亡立即终止，不继续开战或发奖。陷阱目前只记录类型，不在模板阶段实现伤害或箭头解除。
5. 处理落点对应的接敌触发；有敌人时玩家停在敌人前一格，敌人仍占原格。
6. 需要战斗/事件时创建唯一 `PendingInteraction` 并暂停后续规则；无需外部流程则直接收束。
7. 行动提交时记录一次行动序号，以及分别的成功移动/转向计数；外部结果返回不重复计行动。应用结果和精英事实后建立统一存档检查点，再允许下一行动。恢复与任务业务在对应内容阶段实现。

规则提交与演出分离。动画取消/跳过不应重做伤害、再次开战或再次领物。多对象优先级在统一行动解析器中定义，不能依赖 MonoBehaviour 执行顺序。

### 7.3 “敌人前一格”的明确模型

敌人的 `OccupantCellId` 与 `ApproachCellIds` 分开。生成时按走廊入口方向指定接敌格；可见范围由视线系统决定。

- 走到接敌格才请求战斗；相邻但隔墙、不存在连接、不满足入口方向都不触发。
- 敌人未解决时不能直接进入其占位格。
- 同一接敌格不默认允许两个敌人同时触发。首版生成校验拒绝此冲突；未来需要伏击组时显式做一个遭遇对象。
- 起点不能已处于强制接敌中；否则必须有专门的开局遭遇规则。
- 战败、取消、退出重进、邀请成功都不能被当成“从格子删掉 level 即完成”。

### 7.4 与战斗/事件的最小边界

`EncounterRequest` 至少包含：`InteractionId`、`SourceObjectId`、该对象的遭遇次数、已解析敌人组/关卡 ID、返回格位与朝向、结算策略。

`EncounterOutcome` 使用具名结果：`Defeated`、`Recruited`、`Disengaged`、`PlayerDefeated` 等。当前系统没有的结果在适配层明确报告不支持，不能先把 `Recruited` 映射为杀死敌人。

- 二层对象只生成请求，不直接调用场景加载或 `HandSystemUI` 私有方法。
- 适配器负责启动现有流程，并在流程结束时返回一个结果。邀请判定以后在战斗/对话能力内实现；地图只保存结果。
- 二层使用显式 `EncounterCompletionPolicy` 决定战后奖励、是否开商店以及是否结束整局；不能无意继承一层的“战后自动商店/Boss 即通关”。
- 一个 `InteractionId` 的结果最多应用一次；对象版本/遭遇次数不匹配的迟到回调被拒绝。
- 返回二层时复用同一地图实例，不重新生成；清理战斗临时牌与状态，保留玩家本局成长和地图对象状态。

## 8. 行动时钟、对象状态与任务事实

### 8.1 不把“运动”直接实现成每帧更新

已确认探索行动与战斗回合分开计数，不自动互相换算。详细设计在 `ExplorationProgress` 中分别保存行动序号、成功移动数和转向数；这些是行动事实，不先把其中任何一个宣称为敌人恢复回合。真实秒数、帧数、界面停留时间不作为当前规则；具体行动成本与恢复时机在该功能进入实现时确认。

规则方法接收明确的时钟值，需恢复的对象登记到调度器；不要每个墙物/地面都挂 Update。初版规模很小时可用清晰的集中遍历，性能优化以实际数据为准。

### 8.2 状态不要压成单一 completed

| 对象/事实 | 建议状态 |
| --- | --- |
| 敌人 | `Active / InEncounter / Defeated / Recruited`；另存遭遇次数与可选 `respawnAtAction` |
| 陷阱 | `Armed / Disarmed`；伤害/负面种类由定义引用 |
| 恢复物/一次性奖励 | `Available / Claimed`；领取结果与领取次数按实际需要保存 |
| 持续地点 | 保存自己的交互阶段，不强制商店“进去一次就 Completed” |
| 领域解锁 | 曾击败或成功邀请的指定精英 ID、分别记录的结果与出口条件结果；不读取敌人当前是否 Active 替代历史事实 |
| 发现信息 | 未发现、已发现、当前可见，独立于业务状态 |
| 旅程目标 | 方舟方案、洪水通路状态、同行 AI ID 集合、是否已执行离开 |

恢复敌人建议仅从 `Defeated` 回到 `Active`；`Recruited` 不恢复成敌人。恢复时是否再次奖励待确认。恢复位置被玩家占据时建议延迟恢复，不原地无限强制开战。

### 8.3 陷阱/箭头只记录，暂不实现

已确认本阶段仅记录“经过产生伤害或负面、可用对应箭头剪除”的候选地图对象类型，不实现其具体规则。箭头选择、消耗、补充、匹配序列及附魔影响均暂停讨论，不作为对象骨架开工前提。

本阶段不新增探索手牌、探索牌堆、地图用牌 UI、`UseArrow` 命令、箭头专用接口或专用存档字段；不为这些未定玩法创建空实现。未来明确规则后，再通过通用对象能力接入。

战斗暂参考第一层的牌组、抽牌、出牌与战斗状态流程，复用现有能力；不因探索额外引入一套手牌，也不修改现有战斗箭头语义。战斗复用不等于已经批准二层战后自动商店、奖励与通关策略，后者仍单独配置。

## 9. 领域氛围、地形拼装与场景规约

分开三个配置来源：

1. `RegionDefinition`：地点身份、角色/敌人池、环境风格引用。
2. `StripLayout`：直线、转向、交叉口、长度、墙面锚点等几何事实。
3. `DungeonVisualStyle`：只读适配现有 `StripDungeonThemeDefinition` 和通用尺寸配置，提供地面、墙面、天花板与装饰引用。领域直接引用现有主题；未来天空/音乐等新需求可加环境配置，不先建一套重复的 `MapThemeDefinition`。

生成器输出结构，拼装器据结构选择组件；表现切换器根据玩家所属领域做氛围过渡。太空的“无围墙”是显示配置，不自动把所有方向变成可走区域；逻辑边界仍由连接定义。

- 领域边界与交叉口有明确样式规则；不取 `stripIds[0]` 作为长期权威。
- 展示变体在生成时确定或使用独立确定性随机源；刷新 View 不消耗玩法随机数。
- 静态 UI 面板、容器、小地图界面与浮层在 Scene 中搭建，Inspector 绑定；不要沿用原型运行时 new 全套 UI 的方式。
- 3D 程序地形和地图对象按生成结果实例化美术批准的组件 Prefab；这是地图内容生成，不意味着可以动态重建 UI 或修改既有美术资产。
- 地图对象 Prefab 含具名锚点组件与刷新脚本；引用序列化绑定，不按 GameObject 名字/路径搜。
- 不在代码硬编码颜色，不运行时写回美术设定的按钮文字或视觉值。环境渐变由美术配置的资源/参数驱动，不修改源材质/SO。
- 局部揭示/对象变化只刷新受影响的 View，不以销毁整张地图来重置对象。首版不先引入流式加载、大型池化框架或全局美术重做。

## 10. 存档、确定性与结果只应用一次

### 10.1 新快照，不侵入旧格子含义

建议在现有运行档中新增可选 `SecondFloorSaveData`，拥有独立 `schemaVersion`；外层版本迁移由现有存档入口统筹。旧一层档不含此字段时仍走原逻辑，不能默认转成二层。

必须保存：

- 完整生成结果：地图/领域/条带/格位/显式连接/门禁/序列映射、对象定义与实例 ID。
- 玩家位置、朝向、发现信息、行动计数。
- 对象类型对应的具名状态 DTO、恢复计划、遭遇次数、精英历史和任务/同行者事实。
- 本局已解析内容（包括敌人组）、必要随机状态，保证重载不会重新抽内容。
- 未完成交互的请求 ID、源对象、所处阶段、外部流程快照及结果是否已应用。

seed、生成器版本、配置版本用于复现和诊断，但**正常读档恢复快照，不用当前配置重新生成**。不能因后来调整模板而让老存档的门、对象位置和奖励改变。

### 10.2 类型与引用恢复

- 保存显式、稳定的类型标识，如 `enemy`、`trap`，通过白名单映射到 DTO/构造入口；不把 CLR 全限定类型名写进档，不开启任意类型反序列化。
- 对象专有状态用具名 DTO，不建设 `Dictionary<string, object>` 万能状态包。工厂和存档映射需成对登记并测试。
- 先创建全部实例，再解析 ID 引用与重建索引，最后校验。不能把 Unity 实例 ID、Transform 或 MonoBehaviour 引用写成持久身份。
- 必要定义缺失、对象类型未知、引用断裂时输出明确诊断并保留原存档，不静默删掉敌人或遗物继续覆盖保存。

### 10.3 检查点与中断恢复

最小检查点：完成一次探索行动；启动外部流程前；应用外部结果后；切换场景前。

一次提交中，玩家资源变化、地图对象状态、任务事实和交互收据必须一起形成同一运行档快照；复用/加强现有临时文件写盘方案，并保留可恢复的上一检查点。

中断恢复必须显式分流：尚未启动的请求重新派发；已启动流程恢复其快照；已应用结果不得重发奖励。即使两个对象共用同一个 LevelData，也能凭 ObjectId/InteractionId 回到正确对象。首版不承诺任意动画帧精确续播，但必须明确回到最近安全逻辑检查点。

## 12. 实施阶段与每阶段验收

| 阶段 | 交付 | 必须验证 | 明确不做 |
| --- | --- | --- | --- |
| P0：审定规约 | 本方案、关键产品选择、稳定 ID 与触发/行动顺序约定 | 样例走查能解释交叉点、门禁、接敌、中断恢复 | 不改游戏 |
| P0.5：场景副本（R0） | 复制现有第一人称场景为2层制作测试，保留参数/资源引用 | 副本同seed可运行；源场景不变 | 不另起空白场景、不改美术参数 |
| P1：副本内对象与探索骨架（R1） | 最小领域/条带/格位/连接/对象、Session、PrototypeLayoutAdapter和最小输入接线 | 副本实际可移动/转向且只有一套输入；原seed拓扑一致；规则测试通过 | 不接战斗，不做具体房间 |
| P2：展示兼容闭环（R2） | GeometryPlan、现有主题适配、固定Scene UI、对象View；核查Scribble生命周期 | 同seed画面对照；移动不Rebuild；局部边界更新；UI真实命中；无重复初始化 | 不擅改美术参数；密度/分段变化单独审批 |
| P3：快照（R3，可独立于视觉审阅） | 完整对象快照、稳定ID与定义引用、恢复失败处理 | 同定义多实例独立、重载一致；损坏引用/未知版本不覆盖旧档 | 不先覆盖用户运行档 |
| P4：正式生成模板（R3） | 提取旧纯布局、领域/序列映射、奖励终端与门禁 | 多seed连通+进度可解；所有跨域边受控；无意接触不通行 | 不锁死四分区/旧尺寸，不沿用旧端点内容配额 |
| P5：纵向集成 | 一个测试遭遇与一个简单交互往返、结果策略、存档检查点、入口切换 | 战斗→结果→原地图；重复回调无副作用；暂停/退出重进可恢复；一层回归 | 不自动加入发布构建/改默认入口 |
| P6：内容生产 | 按模板逐个接入地点、邀请/遗物/方舟任务等系统 | 每类型的状态与存档用例、关键旅程可完成 | 具体房间另行拆任务 |

先复制场景，再在副本逐步接入对象契约与现有seed适配；同步用手工小地图测试规则。每批都有副本中的可见结果，完成展示兼容后再替换正式生成规则。详细批次采用改造实施案R0～R5，P5对应R4，P6及实测驱动优化对应R5。不要同时写完全部房间才发现行动或存档边界错误。

## 13. 验证清单与首版完成定义

### 13.1 数据/规则 EditMode 测试

- 地图对象 ID 唯一、引用完整、交叉点只有一份状态，格位槽位无非法冲突。
- 同 seed + 同版本/同配置输入产生一致结构和解析内容；遍历/排序使用稳定顺序，不能依赖 HashSet 枚举结果。表现刷新不影响玩法随机。
- 条带序列映射顺序合法、每条带终端地点存在、共享连接不重复生成/触发对象。
- 领域出口条件可达且无循环锁死，所有跨域边受规则管控；关键目标不会放在自身门禁后。
- 前一格接敌、隔墙不触发、敌人占位阻挡、重复输入/回调不重复开战；用测试替身验证通用触发顺序，不以实现陷阱作为验收前提。
- 失败行动不扣资源不推进时钟；恢复只影响指定对象，不撤销永久解锁事实。
- 存读往返、同定义多实例、相同关卡多对象、未完成遭遇恢复、结果重复、未知定义/版本/损坏引用的处理。

### 13.2 PlayMode/人工验收

- 一条完整路径：入口→点击中间前进/左右原地转向→接敌→按一层战斗方式结算并返回→回原格位/朝向→通过精英门禁→测试终端交互→存档重进；不包含陷阱解除或探索手牌。
- 点击 UI 时不误触前进/转向；转向只改朝向，不侧移；前进被阻挡时位置不变。
- 第一人称敌人提前可见，接敌时位置正确；地图发现与当前可见区别清晰。
- UI 真正可点击，关闭面板/遮罩后恢复底层输入；忙碌时不能穿插移动。
- 领域过渡的天空、材质、音乐与装饰由美术验收；不把“脚本执行成功”当作观感通过。
- 一层原有移动、战斗奖励/自动商店、教程与旧档恢复保持原行为。

**模板阶段完成定义：**能添加一个新配置领域和一条新序列而不修改核心流程；能新增一个规则不同的测试对象而不把判断塞进 UI/Session；完整存读恢复同一地图状态；最小遭遇能正确往返。不以“候选房间都已实现”作为模板完成标准。

## 14. 开工前要确认的产品问题

已确认：Boss/商店/休息各自独立，不属于奖励格；成功邀请精英也满足通行条件；探索行动与战斗回合分开计数；探索点击中间前进、左右原地转向；战斗暂参考第一层，不增加探索手牌。

陷阱/箭头相关内容仅作类型记录，其使用、补充、消耗、匹配及附魔影响暂不实现，也不是模板阶段的待决阻塞。以下问题仅在相应功能进入实施范围时再确认，不要求现在细化全部房间。

| 问题 | 建议起点（未批准） | 影响 |
