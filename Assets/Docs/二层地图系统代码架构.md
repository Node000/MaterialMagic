# 二层地图系统代码架构（详细设计稿）

> 状态：代码级提案，尚未实现，不是现有 API 说明。
> 上位需求与脑暴归档：[二层地图系统实现方案](二层地图系统实现方案.md)。本文负责类、数据、调用顺序和实施边界；遇到差异，以用户确认的规则为准。
> 本轮只产出设计和调研，不新增 C#、不修改场景/Prefab/配置、不改发布入口。
> [现状调研与改造实施案](二层地图现状调研与改造实施案.md) 补充来源、运行观察、几何生命周期和迁移批次；先适配旧布局与现有主题，再提取生成，不按绿地工程重写。

## 1. 范围与工程选择

### 1.1 已确认的产品约束

- 中间点击前进一格，左右点击原地转向；不靠打牌移动，不新增探索手牌。
- 地图由条带组合，条带对应有序内容，终端保留奖励格；Boss、商店、休息分别独立，不是奖励格的变体。
- 领域围绕精英组织；击败或成功邀请满足条件的精英，均可取得通行资格；两种结果分别保存。
- 探索行动与战斗回合独立计数。
- 战斗暂复用第一层规则与手牌流程。具体房间、陷阱效果、箭头解除/消耗/补充/匹配暂不实现。

### 1.2 本设计采用的工程选择（不是新增玩法承诺）

1. 普通 C# 对象负责规则，MonoBehaviour 负责输入、显示和连接现有系统。
2. 地图内部采用直接、只读的对象引用，持久化时转换为稳定 ID；不让业务代码反复手写 ID 查找。
3. 结构在生成/读档后冻结，运行时只改变探索和对象状态；首版不支持任意增删地形。
4. 首版条带沿用现有原型的直线定义。交叉处转向进入另一条带；不建立第二套“折弯逻辑条带”。未来真有跨拐角序列需求再加路线编排对象，不改变 Cell/Connection。
5. 允许 `Vector2Int` 作为坐标，不引入自制数学框架。方向用具名枚举，避免到处计算向量旋转。
6. 暂不新增 asmdef：现有 PlayerState、BattleManager 等位于默认程序集，立即拆程序集会牵涉无关迁移。先通过目录、命名空间和测试约束依赖。
7. 无全局二层单例、无全局事件总线、无 ECS、无反射式对象发现、无通用脚本语言。
8. 首批只创建实际使用的类型；本文标注“后续”的能力不提前建空类。

### 1.3 现有代码事实与并行工作

当前 `Assets/Scripts/HandSystemUI.cs` 和 `Assets/Scripts/RunSaveSystem.cs` 已有其他改动，不能用旧版本覆盖。现场读取发现运行档当前版本为 4，玩家快照已含遗物与待选遗物，保存还要求 `player.Relics.IsSettled`。本设计不把旧知识中的版本 3 作为迁移基线；实施时再次读取最新文件。

## 2. 依赖方向与运行所有权

```text
Definitions（SO配置） ──> Generation ──> Domain（本局对象）
                           │               ↑
                           └──校验─────────┤
Exploration（行动会话） ─────────────────────┘
       ↑                  ↑
Presentation          Integration（现有战斗/玩家/保存）
       └──────── SceneController 组装 ────────┘
Persistence <──转换── Domain + Exploration；只产出DTO，不直接写文件
```

- Domain 不引用 HandSystemUI、GameObject、Input、SceneManager、UIManager 或静态当前局。
- Session 不调用 Unity 协程、加载场景或写盘；返回行动结果和外部流程请求。
- SceneController 是组装入口：显式构造对象并绑定 Inspector 引用，负责协程和错误展示，不判断各房间业务。
- Integration 持有外部能力，Persistence 负责转换，现有 RunSaveSystem 继续拥有槽位和最终写盘。

### 2.1 同一局只有一个玩家与一个地图会话

```text
SecondFloorSceneController（Scene内入口）
├─ SecondFloorSession（普通C#）
│  ├─ DungeonMap
│  ├─ ExplorerState
│  ├─ ExplorationProgress
│  └─ PendingInteraction（至多一个）
├─ PlayerState（复用本局实例，不由Session再创建）
├─ LegacyBattleFlowAdapter ──> HandSystemUI / BattleManager
├─ SecondFloorSaveAdapter ──> RunSaveSystem
└─ Input / WorldView / ExplorerView / MinimapView（Inspector绑定）
```

首个纵向集成建议同一测试 Scene 切换探索与战斗显示，不为每个敌人加载一次场景。两种显示存在于不同根节点，切换只改变显示和输入门控，不复制 PlayerState；切换时使用已有面板显隐能力，不直接停用正在结算的协程宿主。

不先做 DontDestroyOnLoad 会话服务。正式跨 Scene 入口走完整快照恢复；这与同场景暂停显示使用同一份状态契约。

## 3. 核心对象：字段、职责与不变量

下列字段为建议的只读属性或私有字段，签名为契约示意，不是可直接复制编译的完整代码。

### 3.1 身份与方向

- 所有地图实体使用本图内唯一、正整数 `Id`；0 代表无引用。不同类别也不复用 ID，以便诊断。
- 定义使用显式稳定字符串 `DefinitionId`，如 `region.dream_bubble`；禁止用文件名、资源路径或 CLR 类型名当身份。
- `MapInstanceId` 为本次地图实例身份，创建后存档保持不变；跨图回调必须同时检查它。
- 生成器用稳定顺序分配实体 ID；不使用 GetHashCode、字典枚举顺序或 Unity InstanceID。
- `Facing` 为 `North/East/South/West`，`DirectionUtility` 统一实现 `TurnLeft/TurnRight/ToOffset`。每次转向 90 度、位置不变。

暂不引入六套 ID 包装结构；参数名、对象引用与加载校验提供约束，出现真实混用风险后再演进。

### 3.2 DungeonMap：结构与唯一实例

| 属性/索引 | 用途 |
| --- | --- |
| MapInstanceId、GenerationInfo | 图身份、seed、生成器/配置版本 |
| Regions、Strips、Cells、Connections、Objects | 对外只读实体集合，稳定顺序 |
| StartCell、StartFacing | 初始探索位置与朝向 |
| cellByPosition、entityById | 位置/身份查找 |
| connectionByCellAndFacing | 查询当前朝向能否走到另一格，双向边生成两个查询项 |
| approachTriggersByCell | 进入接敌格后快速找到候选对象 |

建议入口：

```csharp
DungeonCell GetCell(int cellId);
bool TryGetCell(Vector2Int position, out DungeonCell cell);
bool TryGetConnection(DungeonCell from, Facing facing, out DungeonConnection connection);
IReadOnlyList<EnemyMapObject> GetApproachEnemies(DungeonCell cell);
MapObject GetObject(int objectId);
```

用 `DungeonMapBuilder` 组装并校验，`Build()` 成功后冻结结构；不公开 AddCell/RemoveObject 让运行中任意脚本改图。未知 ID 在外部输入返回具名错误；内部已校验引用失效视为程序错误，不静默返回另一格。

### 3.3 DungeonRegion：领域不是房间管理器

属性：`Id`、`DefinitionId`、`ThemeId`、`Strips`、`Cells`、`ExitConnections`、`GateEliteObjects`。

- 一个 Cell 只归属一个 Region；跨领域通过 Connection。
- ThemeId 是明确解析的领域风格，不再取交叉点第一个条带的主题。
- 门禁读取 `ExplorationProgress` 中的永久精英结果，不读取“敌人此刻是否活着”。
- 方舟任务和具体地点事件暂不做 Region 子类，也不在 Region 塞一个任意字符串 flag 字典。

### 3.4 DungeonStrip：直线有序结构

属性：`Id`、`Region`、`SequenceDefinitionId`、`OrderedCells`、`EntryCell`、`RewardEndCell`、`ContentBindings`。

`ContentBinding` 是小型值数据：`SlotKey`、`Cell`、`Object`。它表达模板槽位落实到哪一格/对象；没有生成内容的空位不创建空 MapObject。

不变量：

- OrderedCells 连续、共线、无重复；相邻格必须存在显式连接。
- 同一个交叉 Cell 可以被多条 Strip 引用，但实体与地图对象只有一份。
- 奖励终端是结构角色，不是父类。Boss/Shop/Rest 不因在端点就成为 Reward。
- 序列顺序只用于生成和展示，不自动禁止倒走；若强制内容先后需要明确门禁。

### 3.5 DungeonCell 与 MapPlacement

`DungeonCell`：`Id`、`Position`、`Region`、`Strips`、`Objects`；不含 LevelData、isBoss、isCompleted。

`MapPlacement`：`Cell`、`Slot`、`SurfaceFacing`。

Slot 首批采用绝对空间语义：`Ground / Occupant / Destination / Wall`。Wall 的 SurfaceFacing 指定北/东/南/西壁，避免“左墙”随玩家转身发生歧义；对象显示朝向另由 Prefab 锚点转换。Destination 是摆放槽，不表示奖励类别。

- 一槽容量与冲突由放置校验定义；首版同一 Occupant 只允许一个阻挡对象。
- 终端格通过 Strip.RewardEndCell 标识，不通过 Cell 的通用枚举混合敌人/商店/奖励分类。
- 奖励/商店/休息各自是不同的未来地点定义或行为，底层都是可摆放对象，不强迫每个格位只能有一个业务类型。

### 3.6 DungeonConnection 与 RegionGate

`DungeonConnection`：`Id`、`A`、`B`、`DirectionFromA`、`TravelMode`、可选 `Gate`。

- 首版只允许坐标相邻的四方向连接；不做传送或长距离边。
- 双向通行是一个连接实体，索引有两个方向，避免两条边状态不一致。
- `CanTraverse(from, progress)` 返回 `PassageCheck`（Allowed、BlockReason、GateId），不通过 View 是否有墙来推断。
- 门禁可按方向约束：首版用“指定来源领域→目标领域”的规则；是否回程也锁由定义显式写出，不能因用了双向边意外全锁。

`RegionGate` 是当前唯一需要的具体条件对象：SourceRegion、TargetRegion、GateEliteObjects、MinimumResolvedCount（首版1）、方向规则。满足条件是指定精英曾 `Defeated` 或 `Recruited`。

不建立通用 Condition AST、All/Any 编辑器；有第二种真实门禁再抽象接口。

### 3.7 MapObject 与 EnemyMapObject

`MapObject` 薄基类只含：Id、DefinitionId、Placement、Revision；不放通用 Completed，不提供几十个空 virtual 钩子。

首批实际业务子类仅 `EnemyMapObject`：

| 字段 | 含义 |
| --- | --- |
| State | Active / InEncounter / Defeated / Recruited |
| EncounterOrdinal | 本对象第几次遭遇，用于拒绝旧结果 |
| EncounterSpec | 已解析关卡 ID、敌人组索引、难度上下文、结算策略引用 |
| ApproachBindings | 接敌 Cell 与必须面向的方向；同格不同朝向可不同 |
| CountsForRegionGate | 是否计入所属领域通行资格 |

具名方法：`CanBeginEncounter(context)`、`BeginEncounter(interactionId)`、`ApplyEncounterOutcome(outcome)`。这些方法校验合法迁移并增加 Revision，不直接扣玩家生命或发奖励。

状态迁移：

```text
Active → InEncounter → Defeated
                     → Recruited（未来邀请流程产出）
                     → Active（明确取消且无结算）
                     → InEncounter保持，Session结束（玩家战败）
```

邀请目前只定义并测试结果应用契约，不实现邀请按钮/说服计算。恢复、陷阱、NPC、商店、Boss、奖励、休息只有类型规划，不提前创建运行类/DTO。测试通用对象能力的 `ProbeMapObject` 放在测试目录，不进正式内容工厂和配置。

### 3.8 ExplorerState 与 ExplorationProgress

`ExplorerState`：CurrentCell、Facing；只允许 Session 通过 `MoveTo/TurnTo` 改变。

`ExplorationProgress`：

- `ActionSequence`：每个被接受的玩家行动递增一次，用于去重与顺序追踪，不宣称它就是敌人恢复回合。
- `SuccessfulMoveCount`：每次有效前进一步加一。
- `TurnCount`：每次有效转向加一。
- `DiscoveredCellIds`：已发现集合。
- `EliteResolutionRecords`：精英对象 ID、结果、首次满足行动序号；同一对象不重复增加通行计数。

这样可保存行动事实，不必在未定玩法前写死“转向耗一回合”。恢复机制将来从这些事实选择时钟，不与战斗回合自动换算。`VisibleCellIds` 是派生显示数据，转向/载入后重新计算，不作为永久发现的替代。

旅程目标当前只保留文档，不提前建带空方舟字段的 JourneyProgress；正式任务出现后新增具名对象并挂到 Session。

## 4. 定义层：只配置数据，不执行行为

### 4.1 正式生成所需 SO 集合（R3按需创建）

| 类型 | 首批字段 | 说明 |
| --- | --- | --- |
| DungeonDefinition | DefinitionId、ConfigVersion、RegionSpecs、RegionLinks、StartRule、GenerationLimits | 一张图的配方，不是本局实例 |
| RegionDefinition | DefinitionId、Theme引用、StripTemplate候选、EnemyEncounter候选、EliteEncounter候选 | 领域主题与内容来源 |
| StripSequenceDefinition | DefinitionId、LengthRange、Slots、RewardEndRule、连接锚点约束 | Slot 具备稳定 Key、种类/候选引用、顺序、间距、是否必选 |
| EnemyMapObjectDefinition | DefinitionId、Encounter候选、ViewPrefab、接敌约束 | 生成后解析具体关卡与敌人组 |
| 现有 StripDungeonThemeDefinition（复用） | 现有主题ID、地面/墙/顶与装饰引用 | RegionDefinition直接引用；DungeonVisualStyle只读适配通用尺寸，不新建重复主题SO |
| MapContentCatalog | 上述定义的显式引用列表 | 构建只读索引，检查重复/缺失ID；不按名字查资产 |

首批序列允许空通路、测试遭遇、终端奖励位置声明。尚未实现的房间只可在内容规划清单描述，不能以“Unknown→通用空对象”假装已实现。正式发布配置引用了未支持类型时，生成必须报 UnsupportedContent；骨架测试图可只声明终端位置，不据此声称奖励可领取。

### 4.2 Definition 与运行快照的边界

生成时将会影响本局规则的选择解析为普通数据：敌人组、对象位置、门禁所依赖精英、接敌格、模板槽位映射。存档保存解析结果，载入不重新抽签。

View、音乐、图标可继续按稳定定义引用解析。首版保存 ContentRevision 并严格校验规则配置版本：缺定义/不兼容变更时拒绝覆盖旧档，保留原档并提示迁移；不承诺当前代码能复现所有历史敌人平衡数值。

不允许把 SO 当本局状态写回；同定义两个 EnemyMapObject 的状态必须独立。

## 5. 行动会话与对象能力契约

### 5.1 Session 公共入口

```csharp
public sealed class SecondFloorSession
{
    public DungeonMap Map { get; }
    public ExplorerState Explorer { get; }
    public ExplorationProgress Progress { get; }
    public SessionPhase Phase { get; }
    public PendingInteraction PendingInteraction { get; }

    public ActionResult TryMoveForward();
    public ActionResult TryTurnLeft();
    public ActionResult TryTurnRight();
    public CompletionResult TryCompleteEncounter(EncounterOutcome outcome);
}
```

暂不加任意 payload 的 Command 类层次。三个清楚的方法足够；通用主动交互真正进入实现范围时再加 `TryInteract(objectId)`。

`ActionResult` 是只读结果：Status、FailureReason、ActionSequence、MapChangeSet、可选 EncounterRequest。Status 首批 `Rejected / Completed / EncounterRequested`。常规阻挡返回错误码，不靠异常控制流程。

`SessionPhase` 首批 `Exploring / AwaitingEncounter / Ended`。单次 C# 解析同步执行，不需持久化 ResolvingAction 状态；重入用内部保护拒绝。演出忙碌由 SceneController 管，不与业务阶段混成同一个 busy。

### 5.2 对象能力接口，先最小化

本阶段落地 `IApproachTrigger`；其余能力在需要测试扩展边界时再加入，不建四个无实现接口凑架构。

```csharp
public interface IApproachTrigger
{
    TriggerCheck CheckApproach(ApproachContext context);
}
```

`ApproachContext` 只含只读地图、位置/朝向、行动类型与已完成结果。`TriggerCheck` 返回 None/EncounterProposal；检查方法不改状态、不随机、不访问 MonoBehaviour。

EnemyMapObject 通过接口返回已解析 EncounterSpec 的提议；Session 统一调用 BeginEncounter 并创建请求。未来 Enter/Interact 能力遵守同样的“先检查→统一提交”原则；新房间行为需要新的外部流程时才增加具名请求，不提前做万能 Effect 字符串列表。

### 5.3 前进顺序：先查通路，再提交一次

1. Phase 必须 Exploring；查询当前 Facing 的显式连接，无连接返回 Wall，不计行动。
2. 检查方向门禁与目标格阻挡。Active/InEncounter 敌人占位不可直接进入；无需地形碰撞判定。
3. 在候选落点按固定优先级/对象 ID 收集触发，验证只会产生一个外部请求。验证失败不移动、不改敌人。
4. 同步提交位置、ActionSequence、SuccessfulMoveCount、发现信息；若接敌，敌人进入 InEncounter，创建唯一 PendingInteraction，Phase 变 AwaitingEncounter。
5. 产生 MapChangeSet 和 ActionResult；Controller 先保存该完整状态，成功后才演出/派发战斗。

当前无陷阱效果，因此不提前实现玩家伤害、死亡中断与多效果事务系统。未来进入格效果放在位置提交之后、接敌开始之前，并为新增规则增加对应测试。

### 5.4 转向和接敌

- 转向原地改 Facing，增加 ActionSequence/TurnCount，不增加 SuccessfulMoveCount。
- 接敌绑定包含 ApproachCell 与 RequiredFacing。进入接敌格且朝向敌人时触发；身在接敌格后转身面对敌人也检查一次，避免“背对进入后永远不触发”。这是本设计的首版触发建议，不改变前一格停下的要求。
- 回战斗后不再自动移动进敌人格；Defeated/Recruited 对象不再阻挡，下次前进可进入原格。
- 同一格/朝向不能绑定两个有效遭遇；生成校验拒绝冲突，不以对象 ID 决定偷偷先打谁。
- 读档不把站在接敌格当成新行动；若有 Pending 则恢复它，没有则等待下一次合法行动。

### 5.5 变更结果与显示通知

`MapChangeSet` 只含受影响 Cell/Object/Connection ID、位置/朝向是否变更、发现集合增量；由一次行动/结果应用产生，不是第二份状态源。

Controller 显式调用各 View 刷新。可以有本场景局部的 Changed 通知，但核心状态不依赖订阅者是否存在；不构建全局事件总线。View 丢失刷新时可从当前 Session 全量重绑恢复。

## 6. 外部战斗契约：复用一层，不复用旧地图推进

### 6.1 请求与结果

`EncounterRequest`：MapInstanceId、InteractionId、SourceObjectId、ExpectedObjectRevision、EncounterOrdinal、ReturnCellId、ReturnFacing、ResolvedEncounterSpec。

InteractionId 使用本图内单调递增 long，创建时保存 NextInteractionId；组合 MapInstanceId 后唯一。

`ResolvedEncounterSpec`：LevelNumericId、EnemyGroupIndex（-1表示非随机组）、ChapterNumericId、IsBossEncounter、CompletionPolicyId。IsBossEncounter 只影响战斗上下文，不代表二层终点。

`EncounterOutcome`：上述身份与版本、Result（Defeated/Recruited/Disengaged/PlayerDefeated）、外部流程完成凭证。玩家生命/金币/牌组由战斗流程维护；Outcome 不携带一份重复资源增量，地图不可再次发同一份战斗奖励。

### 6.2 PendingInteraction 是可恢复状态，不是回调委托

字段：Request、Stage、可选 EncounterOutcome、外部快照引用。Stage 为 Prepared/Running/OutcomeReady；OutcomeReady 表示外部已完成、地图结果尚待应用。应用成功后更新收据并清空 Pending。Session 的 Phase 从 Pending 推导并校验，不允许“Exploring但还有Running”。

流程：

```text
Session 创建 Prepared
  → Controller 保存地图+玩家
  → Adapter 开始并形成可恢复外部快照
  → 保存 Running + 外部快照
  → 现有战斗/奖励结算（明确策略）
  → 外部提供 Outcome
  → Session 校验身份/版本/序号，应用对象结果和精英事实
  → 同一检查点保存玩家+地图+结果收据
  → 清理战斗显示，恢复探索
```

不存在“恰好一次消息投递”的承诺；实现的是**重复调用不重复产生效果**。LastAppliedInteractionId 与每对象 EncounterOrdinal/Revision 检查迟到结果；正常同局严格串行，不需永久增长的消息日志。

### 6.3 结果校验与失败

- 错图、错对象、错遭遇次数、旧版本、未知 InteractionId：拒绝且输出诊断，不改状态。
- 同一已应用结果再到达：返回 AlreadyApplied，不重领、不重开门、不重新播放业务。
- 玩家失败：Session Ended；地图不伪装成胜利。谁负责整局失败记录由外部结算入口唯一执行。
- 适配器不支持 Recruited：不得映射为击杀；当前邀请仅可用测试替身验证存档与门禁。
- Adapter 启动失败：保留 Prepared 请求和安全检查点，显示重试/退出；不能一边把敌人设为已击败一边回地图。
- 保存失败或外部状态未稳定：锁住后续行动/场景切换并保留待保存状态，提供重试，不回滚一半或继续前进。保存协调器返回 Saved/Deferred/Failed；Deferred 等待外部规则结算稳定后重试，不能把延迟保存误判为已成功。

### 6.4 与 HandSystemUI 的必要改动面（后续实施）

| 现有入口 | 风险 | 建议最小接点 |
| --- | --- | --- |
| Awake | 自建PlayerState/RunManager/BattleManager、恢复旧地图、立即ShowLevelSelect | 抽出通用战斗UI绑定与战斗初始化；默认路径保留；外部二层模式等待明确InitializeExternalBattle(context)，不自建第二玩家/地图 |
| SelectLevelEnemyGroup / SpawnBattleLevelEnemiesRoutine | 再抽敌人组导致地图显示与实战不一致 | 外部请求优先使用已解析组；无外部上下文保持一层逻辑 |
| StartBattleLevelRoutine | 调用旧地图隐藏、保存与随机推进 | 外部模式使用注入的显示/保存边界，不调用旧地图；战斗开始/抽牌/敌人规则保持 |
| FinishBattleRoutine | Boss可能立即ShowVictoryPanel | 在共同战斗收尾之后选择一层路径或外部CompletionPolicy，不直接结束二层 |
| FinishReward | 清牌后推进旧地图/自动商店 | 提取共同清理；二层完成后返回Adapter，不ShowLevelSelect、不AdvanceMapNode |
| SaveRunProgress / OnApplicationPause / Quit | 用旧快照覆盖二层字段 | 外部模式路由到统一二层保存协调器；一层保留原路径 |
| OnDestroy | 静态Current清理及订阅 | 明确创建者负责释放；不清理仍由二层宿主持有的本局对象 |

外部模式由 Inspector 上显式配置的启动方式和初始化上下文控制，不能用场景名称字符串猜测。Awake 的被动分支必须在二层自动初始化以前生效，不能赌脚本执行顺序。

建议的适配契约：

```csharp
public interface ISecondFloorBattleFlow
{
    BattleFlowStartResult TryBegin(EncounterRequest request);
    BattleFlowRestoreResult TryRestore(EncounterRequest request, CurrentNodeSaveData snapshot);
    bool TryCapture(out CurrentNodeSaveData snapshot);
    bool TryGetCompletedOutcome(out EncounterOutcome outcome);
}
```

Adapter 通过显式初始化绑定唯一 PlayerState、HandSystemUI 和 BattleManager；不在接口里再传一份玩家快照创建玩家。Controller 轮询或订阅该实例的局部完成通知后调用 TryGetCompletedOutcome；读取结果不自动发奖或清除完成凭证，直到统一检查点确认已应用。首版复用 CurrentNodeSaveData 只限其现有战斗/奖励可表达部分；其不能表达的中间阶段须先补具名 DTO，否则不得宣称可恢复。

首版只有 `LegacyBattleFlowAdapter` 与 `ISecondFloorBattleFlow` 这一条战斗变化边界。不要用调试开战方法凑接入，也不为复用战斗重写整个 HandSystemUI。若公共清理抽取影响一层，必须补回归。

## 7. 生成：清楚的分阶段实现，不做插件框架

### 7.1 三种数据形态

1. Definition：用户配置与资源引用。
2. `DungeonBuildPlan`：生成中的可变草稿，用 ID/坐标和候选数据描述实体，无运行行为。
3. `DungeonMap`：构建/加载成功后的冻结结构与本局对象。

`DungeonMapBuilder` 同时被随机生成、手工测试构图与读档装配使用，因此三者不会各维护一套约束。保存 DTO 不是 BuildPlan，避免以后生成内部重构破坏档格式。

### 7.2 正式生成职责（R3；先完成R1旧布局适配）

```text
DungeonGenerator.Generate(request)
  → BuildRegionPlan
  → BuildStripLayout
  → BindSequenceSlots
  → PlaceSupportedObjects
  → ResolveEncountersAndIdentity
  → ValidateProgression
  → DungeonMapBuilder.Build
```

首版可在一个 `DungeonGenerator` 中以具名私有方法实现；只有阶段明显变大/需要独立测试才拆 RegionLayoutGenerator、StripLayoutGenerator，不预建一堆 IGenerationStep。

- `GenerationRequest`：定义、seed、最大尝试次数；`GenerationResult`：成功地图或阶段/原因/涉及ID/尝试号。
- 输出显式 Connection，不能因两个格子贴近就默认接通。
- 门禁可解性通过迭代：从起点可达集出发，加入可接触精英的可完成事实，再开放对应边，直到稳定；所需对象/出口不可达即失败。邀请过程未实现时测试用“可解决精英”假设，不声称实际玩法已可完成。
- R1先用 `PrototypeLayoutAdapter` 转换旧输出、核对坐标/条带/全部旧邻接，包括意外接触边；兼容图显式记录这些边，正式图禁止其自动通行。
- R3再从原型提取矩形环路与分支的纯布局阶段，不长期复制算法；不直接用旧 LevelType/内容配额冒充新对象生成。
- 无支持的具体奖励行为时可声明奖励终端的结构位置，不能随机放Boss/商店顶替。

### 7.3 确定性

使用小型 `GenerationRandom`（Seed、Step）包装现有 `RunRandom.Range`，每次抽取显式推进 Step。布局、内容、装饰分别使用固定数值盐派生的随机流；不使用 string.GetHashCode 派生种子。

生成实体和候选都稳定排序，ID 分配不依赖哈希遍历。GenerationInfo 保存 seed、generatorVersion、configVersion、尝试号；调试复现要求版本一致。正常读档从完整快照恢复，不调用 Generator。

战斗仍使用玩家已有运行随机状态，不让摄像机/装饰刷新消耗它。生成与战斗流分离是二层工程选择，不改变一层随机逻辑。

### 8.1 输入门控分开命名

Controller 的 `CanAcceptExplorationInput` 取决于 Session Exploring、非演出中、无保存失败、无模态UI、非战斗。一个 press 只提交一次；触屏使用当前手指的 UI 射线/触点身份，不能只依赖鼠标的 IsPointerOverGameObject 默认重载。

静态点击区域、地图UI和容器在 Scene 搭建，Inspector 绑定。现有原型三等分仅作行为参考，不复制运行时创建UI和硬编码颜色的路径。

### 8.2 可见性与已发现

首版 `DungeonVisibility` 可沿 Facing 的显式连接做直线视野（参考原型），墙阻挡、门禁视觉遮挡与观察距离来自明确配置；“门锁着是否能看穿”不能自动等于不可走。

可见性计算不得触发战斗/解锁，发现状态在行动提交时更新。Boss隐藏策略不作为首批硬编码，后续内容实现时接入。

### 8.3 演出中断

规则先同步提交，View 从新状态演出；Controller 在演出期间拒绝后续输入。演出取消时吸附到已提交位置，不重复提交行动。保存读档不恢复 tween 进度，只恢复安全格位/朝向和未完成外部流程。

## 9. 持久化：对象图快照与现有运行档协作

### 9.1 DTO 层级

```text
RunSaveData（现有；保留player/difficulty/runPools等）
└─ secondFloor : SecondFloorSaveData（可选新增）
   ├─ schemaVersion / contentRevision / mapInstanceId
   ├─ generationInfo / nextEntityId / nextInteractionId
   ├─ regions[] / strips[] / cells[] / connections[] / gates[]
   ├─ objectRecords[]
   ├─ explorer / explorationProgress
   ├─ pendingInteraction
   └─ lastAppliedInteractionId
```

`MapObjectRecord` 用 TypeKey + ObjectSchemaVersion + 共有身份/摆放 + `JObject State` 承载编码层的专有数据。State 只能经显式白名单 codec 转成具名 DTO（首批 EnemyObjectSaveData）；JObject 不是运行态万能字段包，也不开放任意 $type/CLR类型名反序列化。

首批实现一个集中的 `MapObjectPersistence`，显式 Create/Write/Read 支持 enemy；新增真实类型时三者同处登记并测试，不为单类型建立反射注册框架。未知类型返回 UnsupportedObjectType，保留原档。

### 9.2 保存与加载 API

```csharp
SecondFloorSaveData Capture(SecondFloorSession session);
RestoreResult Restore(SecondFloorSaveData data, MapContentCatalog catalog);
```

Capture 仅在逻辑稳定边界执行，不从 Transform 抓位置。Restore：版本迁移→基础校验→创建实体→解析引用→重建索引→状态/门禁/请求一致性校验→返回可运行Session。失败返回详细诊断，不边恢复边写盘。

运行对象使用直接引用，DTO 统一使用 ID，构建完成后保证不存在悬空引用。发现集合、精英记录必须引用图中实际存在的对象/格位。

### 9.3 RunSaveSystem 接入原则

- 新增二层明确入口，例如 `SaveSecondFloorRun(context)`，与现有 SaveCurrentRun 共用玩家导出和写盘底座；不为满足 mapNodes.Count>0 伪造一个旧节点。
- 统一写入玩家、地图、当前战斗/奖励快照、遗物待选等状态；不能让地图和玩家各自写不同文件形成半提交。
- 保留现有遗物稳定性要求 `Relics.IsSettled`；不稳定时显式报告 Deferred/Blocked 并待稳定保存，不静默认为已存。
- 拓展 CurrentNode 外部流程信息时必须绑定 InteractionId；单个 levelId 不能区分地图上同关卡的两只敌人。
- 普通一层保存不能清空已存在的 secondFloor 字段；只允许由明确流程切换入口决定当前楼层。外部战斗保存必须路由二层上下文。
- 旧一层档无 secondFloor 保持原逻辑；旧二层PC原型档不能默默当成新对象档，不自动转换。需要迁移时另写明确工具/版本迁移方案。
- 新 schema 从自身1开始；外层运行档版本在实施时基于最新值递增，不能预先写死“升到4”。
- 现有 delete→move写盘不提供完整故障恢复保证；集成阶段增加上一检查点备份/同目录替换并测试中断边界，不能在设计中声称已有原子保存。

### 9.4 Prepared/Running 的恢复

- Prepared 且无外部快照：校验后启动原请求，不增加遭遇次数、不重抽敌人。
- Running：恢复已保存战斗/奖励阶段，不调用普通新开战入口。
- 玩家奖励已变更但地图结果待应用：同一快照必须带 OutcomeReady/外部完成凭证；恢复后只应用地图结果，不再发奖。
- 结果已应用：显示已保存状态，重复结果返回 AlreadyApplied。
- 外部快照缺失/阶段不一致：阻止覆盖保存，显示诊断并允许回上一安全检查点；不默默新开一场战斗覆盖玩家资源。

任何主动退出/场景切换都先经过保存协调器；OnApplicationQuit 只是尽力兜底，不能作为唯一保存点。

| Generation | 稳定seed、门禁可解、精英在锁内可达、终端角色正确、重试有界、无支持类型明确报错 |

| Presentation | 真实点击过滤UI、触屏fingerId、转向不侧移、演出取消吸附、View重绑不重置状态、无墙不越界 |
| Compatibility / Geometry | 原seed全部邻接比对、实际眼高等场景参数保留；移动无Rebuild、局部揭示无关段不变、表面初始化一次、Mesh所有权与1/3/6格规模检查 |
| Regression | 一层开始/继续、战斗/奖励/自动商店、教程、旧档、现有遗物持久化不退化 |

A/B主要用EditMode，C/D补PlayMode和人工视效检查。每次实现按项目预算集中做最低成本检查，未覆盖项如实列出。本轮按用户要求短暂运行旧原型，只完成初始画面与引用网格规模观察，未完成本表行为/性能验收。实际性能优化按R0/R5证据推进，不从网格数直接推断GPU耗时。

**架构验收标准：**人类可以从一个输入方法直接跟到Session、对象规则和结果；新增内容不必改输入/摄像机；新增对象规则不必往Session堆类型判断；地图状态不依赖View存在；读档恢复同一张地图；现有一层流程不被二层接管。

## 12. 设计未决项与非阻塞处理

- 条带端点奖励的具体行为、Boss/商店/休息位置：仅保留结构声明和独立类型，不创建假完成房间。
- 领域数量/连图形态、回程门禁：配置和测试构图显式指定，不默认四分区或全双向锁。
- 接敌转身策略：本文建议面向敌人时触发；具体实施前在最小测试图中确认，不需要先实现房间。
- 探索行动成本/敌人恢复：记录分开的事实计数，不实现恢复调度。
- 战后奖励/自动商店：定义CompletionPolicy边界，纵向集成前选定测试策略，不凭“参考一层”推定经济规则全部照搬。
- 邀请/方舟/结局、陷阱/箭头：内容阶段再设计，不是A/B骨架的阻塞，也不预建空类。

下一步先实施R0场景复制和基线核对，再做A/R1并在副本形成可操作结果：Session移动/转向、PrototypeLayoutAdapter旧seed拓扑比对，配合手工图的接敌、精英通行和重复结果测试。R2几何提取、R3正式生成与R4战斗均持续在2层制作测试副本迭代，不同时改动全部入口。
