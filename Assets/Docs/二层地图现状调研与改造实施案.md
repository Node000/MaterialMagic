## 1. 结论：保留生成和美术基础，逐步替换运行控制

在现有条带布局和手绘资源基础上，逐步提取对象规则、空间构建和展示职责。

推荐路径：

1. 首先复制现有第一人称二层场景 `Assets/Scenes/SecondFloorStripDungeonFirstPersonTest.unity`，保存为 `Assets/Scenes/2层制作测试.unity`，保留源场景作为回归参照。副本是后续地图实际制作和验收的持续入口。
2. 在副本中逐步接入只读布局适配器、新对象地图和Session，每批完成可见的运行结果；证明移动、视线、坐标和地形外观可以一致。
3. 从现有地形方法提取“空间构建计划→组件实例化”，保留手绘风格和参数来源，优先解决重复生成与网格规模。
4. 再增加领域、精英门禁和条带内容序列的正式生成规则，不让旧的端点普通内容规则冒充新设计。
5. 最后接现有一层战斗和统一运行档；具体房间仍延期，不新增探索手牌。

原先“先写很多新配置与新生成器再做显示”的顺序需要收敛：先让同一现有 seed 在新运行控制下可核对，再替换布局/内容策略。

## 4. 外部学习：实际来源、适用范围与决定

以下均已读取正文或指定章节；未安装第三方插件、未下载运行外部示例、未复制外部源码。Unity官方HTML返回较多标签，但已读取其正文段落，不仅搜索摘要。

### S1：图与表示分离

来源：[Red Blob Games — Introduction to A*](https://www.redblobgames.com/pathfinding/a-star/introduction.html)，Representing the map / Breadth First Search；访问2026-11-12。

- 资料说明：算法只认识节点和边，不认识3D房间/门模型；等成本全图可达分析可用BFS。
- 采用：Cell+Connection是权威；生成门禁检查与运行移动查询同一套邻接数据。当前一步移动不需要NavMesh或完整A*。
- 不采用：没有移动敌人、自动寻路需求时不额外接NavMesh，也不建设通用寻路服务。
- 验证：两格贴近却无连接时不能走；CanTraverse与BFS得到一致通路。不同移动成本未来再讨论。

### S2：环路、可调生成与端点取舍

来源：[Bob Nystrom — Rooms and Mazes](https://journal.stuffwithstuff.com/2014/12/21/rooms-and-mazes/)，What’s in a dungeon / Looking for a connection / Uncarving；访问2026-11-12。

- 资料说明：连通性与环路有不同意义；纯树状图增加回头路；通过区域连接与少量额外边可控制环路。文章的另一做法是删除死路。
- 采用：确认现有初始环路可继续使用，正式生成应先建立领域/进度关系再安排空间。
- 不采用：不能照抄“删掉所有死路”，因为本项目条带端点奖励本身有意义；不能照搬其大房间/迷宫风格替换直线条带。
- 验证：终端仍保留，领域门禁不被新增环路绕过，回头路径长度作为后续设计指标而非硬编码限制。

### S3：行动驱动与表现分离

来源：[Bob Nystrom — A Turn-Based Game Loop](https://journal.stuffwithstuff.com/2014/07/15/a-turn-based-game-loop/)，Slicing up / Actions / Fat fingers；访问2026-11-12。

- 资料说明：界面注入行动，规则不读取输入；规则执行与选择分开；非法行动不一定消耗回合，判断应在规则内。
- 采用：Session具名前进/转向方法，规则先提交，View再演出；撞墙失败不改位置/成功行动计数。
- 不采用：它的全Actor能量调度与移动怪物速度系统不符合当前范围，不引入；三个行动不需要十九种Command子类。
- 验证：无View也可测试行动；插值取消不会多走一步；探索计数不受帧率和战斗回合影响。

### S4：流程图→空间→主题，边界门墙切换

来源：Dungeon Architect作者文档（Unity，页面未标固定版本；本项目未使用该插件），[Design a Grid Flow Graph](https://docs.dungeonarchitect.dev/unity/grid-flow/gridflow-design-graph/)、[Connections](https://docs.dungeonarchitect.dev/unity/snap-grid-flow/sgf-connections/)、[Key Lock System](https://docs.dungeonarchitect.dev/unity/grid-flow/gridflow-key-lock-system/)；访问2026-11-12。

- 资料说明：先做抽象主/支路线再转tilemap；墙可作为格边；门禁从节点移到连接，防绕路；Connection拥有门/墙显示，使用清楚的局部原点和朝向。
- 采用：生成分阶段；BoundaryBinding明确边界位置/朝向/视线/门禁；标记点用具名类型和Inspector绑定，既有主题负责资源。
- 不采用：不购买/引入Dungeon Architect、不建设节点编辑器、不复制Collider碰门判定；本项目使用格行动规则，不靠物理触发开门。
- 验证：跨域所有边受条件控制；同一边界只显示一次；门外向/墙厚与缝隙有规范测试。这里只借鉴结构，不宣称其保证能迁移本项目手绘资源。

### S5：合并网格的局部剔除代价

来源：[Unity 2022.3 — Manually combining meshes](https://docs.unity3d.com/2022.3/Documentation/Manual/combining-meshes.html)，Warning段；访问2026-11-12。

- 资料说明：手工合并后无法逐原网格剔除；一部分可见时整块被绘制。
- 采用：保留“连续段拼装”，但长段按明确边界/预算拆分；交叉、主题、门禁、隐藏边界都作为断点。
- 不采用：不把整图手绘透明层Combine成一个超大Mesh来追draw call。
- 验证：同seed记录Renderer包围盒、可见网格量、剔除行为和视觉接缝；段长不是越大越好。

### S6：URP合批不是GPU实例化的叠加按钮

来源：[Unity 2022.3 — SRP Batcher](https://docs.unity3d.com/2022.3/Documentation/Manual/SRPBatcher.html)，Compatibility / How it works / Profiling；[GPU instancing](https://docs.unity3d.com/2022.3/Documentation/Manual/GPUInstancing.html)，SRP Batcher / Performance implications；访问2026-11-12。

- 资料说明：SRP Batcher主要减CPU渲染状态切换成本，不保证draw call合一；常规GameObject路径SRP Batcher优先于GPU instancing；实例化要求同Mesh/Material，MPB会影响SRP Batcher兼容。
- 采用：先复用共享材质、检查自定义Shader兼容和Frame Debugger实际路径；有大量同网格装饰才单独比较实例化。
- 不采用：不为了“优化”给所有对象MPB或破坏Shader兼容；独特生成网格不因勾选材质就自动成为同Mesh实例。
- 验证：实际draw事件/批次原因、RenderThread和GPU计时，而非仅勾选状态。当前已观察2种共享材质、SRP开启，不能据此断言draw call已经很低。

### S7：先定位CPU/GPU与透明层开销

来源：[Unity 2022.3 — Graphics performance fundamentals](https://docs.unity3d.com/2022.3/Documentation/Manual/OptimizingGraphicsPerformance.html)，Before you begin / Reducing CPU / Reducing GPU；访问2026-11-12。

- 资料说明：先profile，CPU提交、GPU几何和透明overdraw需分别处理。
- 采用：分开记录生成峰值、稳定帧、局部揭示；透明手绘层的overdraw/Bounds与顶点规模一起检查。
- 不采用：没有测量不承诺对象池、LOD、分区加载或遮挡剔除必然提升帧率；不通过改颜色/线密度/Shader渲染队列偷偷换外观。
- 当前限制：数个Unity遮挡文档地址失效，未取得足够正文；烘焙遮挡不列为已验证选择。后续确有需求再查，不把相机OcclusionCulling勾选当作运行随机图已有遮挡数据。

### S8：触屏与UI命中

来源：[Unity UI 1.0 — EventSystem](https://docs.unity3d.com/Packages/com.unity.ugui@1.0/api/UnityEngine.EventSystems.EventSystem.html)，IsPointerOverGameObject(int) Remarks、RaycastAll；访问2026-11-12。

- 资料说明：无参重载使用pointerId=-1的左鼠标，触屏应传具体pointerId。
- 采用：复用Legacy Input，按当前手指检查；UI点击与探索输入隔离，按钮验收走真实RaycastAll。
- 验证：同一按下不触发两次；点击模态UI不前进、关闭遮罩后可走；真机测试另行进行。

## 5. 改造重点一：拓扑适配而不是复制旧内容

新增 `PrototypeLayoutAdapter`（Integration）接收已生成的 StripDungeonMap，输出 DungeonMapBuilder草稿：

1. 稳定排序旧格位分配CellId，保留坐标、起点、条带顺序与seed，不复制它们的可变实例。
2. 同条带连续两格建立显式Connection；共享交叉Cell复用一个实体，不创建双份。
3. 旧原型当前隐含“坐标相邻可走”，所以适配器必须检查**跨条带相邻但不是连续段/共享交叉的接触边**，列出诊断。兼容快照可明确导入这些旧邻接边以保持原行为；正式新生成器禁止意外接触成为通路。不能静默改变旧seed可达图。
4. Boss侧格/入口用独立兼容边描述；业务隐藏仍是旧原型策略，不生成假Boss房行为。
5. 不把旧isContent/LevelType直接转换为“可领取地点”；仅输出诊断标记/规划占位，正式敌人由明确EncounterSpec构造。
6. 原型无领域归属，适配图可用单个“兼容领域”包住，保留旧逐格样式映射；这只是A/B比对输入，不能声称已有领域玩法。

旧字段/类型不重命名，不改原旧生成器SO和现有测试预期。适配器完成后才提取旧生成器的纯布局阶段给正式新生成器复用，避免长期维护双份算法。

## 6. 改造重点二：GeometryPlan与边界局部更新

### 6.1 新增最少的数据对象

- `DungeonGeometryPlan`：地面段、顶段、墙段、边界段、装饰锚点的只读记录。
- `SurfaceSegment`：SegmentId、类型、起格、方向、长度、VisualStyleId、变体键、空间Bounds。
- `BoundaryBinding`：ConnectionId或边界键、两端格、绝对朝向、通行条件、视觉遮挡策略、局部段引用。
- `ScribbleSurfaceBinding`（新组件/适配描述）：序列化关联结构Renderer、手绘Plane/Grid、装饰锚点与基准尺寸。不能继续“找最大面积Plane当墙纸”。

这些是地形表现数据，不是地图业务对象，不塞进MapObject继承树。

### 6.2 分段准则

保持现有连续段方法；在以下位置断开：交叉点、领域/样式切换、动态门禁或隐藏边界、明确几何预算上限。门框/门墙可单独一个BoundaryView；解锁只更新该边界，不重新计算整个环境。

分段会影响手绘笔触连续性，先保留当前长段输出作对照；分段参数在新适配/预算配置里，不覆写美术Prefab参数。长度上限待代表性1/3/6格视觉与规模对比后选，不凭经验写死4格。

### 6.3 Boss揭示的兼容回归

旧原型仍可保留全图重建作为基准。新运行路径建立边界索引：揭示侧房时只创建/显示侧格表面、更新入口封闭面和相邻受影响墙段、增加对象视图；未受影响SegmentId、网格和变体不变。正式Boss揭示规则以后确定，先用兼容事件证明局部更新能力。

## 7. 改造重点三：手绘网格生成成本

### 7.1 代码证据支持的风险

- Floor和Wall先Instantiate结构Prefab，其中Scribble OnEnable可能生成Mesh，随后只禁用Renderer，不会自动停止组件初始化或释放已生成Mesh。
- Mural再Instantiate同Prefab，创建了重复层级/组件，后续才筛选Renderer；禁用显示不等于没有生成成本。
- `ScribbleTileGrid3D.SetLayoutArea`会立刻Rebuild，Prefab OnEnable也可能先生成一次，需计数验证是否双建。
- `CreateWallMural`把墙宽比例同时乘到FillLineCount与FillSamplesPerLine；对于ParallelScan，在达到上限前网格量大致与两者乘积相关，不应把它当作线性扩展。EdgeGuidedStrokes还受引导点、每点笔划和绕行采样影响，需分别统计，不能统一套公式。
- 地面Columns×Rows×实际生成瓷砖×每砖笔划采样也能产生百万级Mesh。此次最大物体只有名字，未单独归因。
- ScribbleRibbon为Transparent / Blend / ZWrite Off / Cull Off；即使材质少，重叠透明笔触仍可能产生高overdraw，不等于可作为遮挡墙。

### 7.2 先不改画面：生命周期与重复初始化

1. 抽离结构层和手绘层绑定，但保留同一资源和原值；方案获批后通过包装Prefab/适配组件明确引用，保GUID。
2. 若修改共用Scribble API，新增BeginConfigure/EndConfigure或一次性Initialize生成入口，保持原默认行为；二层实例先设布局再Rebuild一次。不能只把组件enabled=false就假定OnEnable从未运行。
3. 不需要显示的副本不生成动态手绘Mesh；不需要的Renderer层不靠运行后全树筛选，按绑定选择路径。
4. 补生成Mesh所有权：谁创建谁销毁；不销毁资产Mesh；缓存共享后必须禁用单实例OnDestroy重复释放。

### 7.3 需要视觉审阅后：密度和分段

- 墙面根据笔划方向的投影跨度计算线数量/采样跨度，不能宽度一个比例重复乘两维；EdgeGuided使用独立策略。
- 地面按世界单位保持瓷砖尺度与笔划风格；不同时拉伸网格尺寸又无约束放大行列采样。
- 必须有单段顶点/索引上限，超过则拆段或明确报告；不可静默降密度。
- 共享网格缓存仅针对同样式、尺寸、seed、采样、引导点与布局输入一致的对象；含动态引导点的实例不共享。先测命中率，未命中就不引入缓存复杂度。
- 任何密度、采样、分段接缝或笔触方向变化先交美术对照审阅，不以性能名义覆盖现有资源。

首版不直接改成贴图墙、合并整图透明网格或全部GPU实例化；这些会改变生产方式或效果，不是无损重构。

## 8. 配置与UI迁移：减少不必要的新SO

### 8.1 复用现有主题而非平行建第二套

`RegionDefinition`首先引用现有 `StripDungeonThemeDefinition`；`GeneralThemeGenConfig`继续作为默认尺寸来源。新代码用只读 `DungeonVisualStyle` 适配器读取它们。

初期不创建独立MapThemeDefinition。未来新增天空/音乐/无墙配置时，优先由RegionEnvironmentProfile补充，不复制地板/墙/装饰列表。已有两个themeId和资源引用不变，不去重重复Prefab条目（可能隐含权重）。

若新组件调整序列化字段，必须先查代码与Unity序列化使用，再迁移；本轮只提方案，没有实施字段迁移。

### 8.2 场景迁移

用户已指定：第一步复制 `Assets/Scenes/SecondFloorStripDungeonFirstPersonTest.unity` 为 `Assets/Scenes/2层制作测试.unity`（计划，尚未创建），直接在副本推进实际地图实现。源场景继续作为旧原型对照，后续不另建空白SecondFloorMapSystemTest场景。

复制在Edit Mode通过Unity资产API进行，为副本生成独立GUID，保留其内部引用、Prefab关联和序列化参数；不手工复制.meta。先确认副本在同seed下保留现有地图、摄像机、输入与外观，再逐步接入新系统。源场景若有未保存工作先保留，不能用磁盘旧内容替代用户工作。

副本初期沿用现有层级和资源，随后按实现批次在副本中补齐或迁移Controller、玩家/摄像机、环境根、探索输入区域、Canvas、状态/调试文本、小地图容器及格位UI。静态UI在编辑时搭好、Inspector绑定；接管后停用副本里的旧输入/运行控制，保证只有一套系统响应。当前18×14可在编辑时建立固定格位控件；地图尺寸变化走编辑工具/人工扩展，不运行时new整套UI。

复制场景不会隔离共享脚本、SO、材质或Prefab：优先以新组件/适配器接管副本，现有资源先只读复用；确需测试专用配置时再显式复制并重绑。共用Scribble代码调整仍须核查其他使用方，不因在副本测试就认为原场景不受影响。

当前Scene eyeHeight实际为0.8，源码默认1.55；迁移优先保留0.8及FOV72、格距3等资产实际值，不按代码默认重播种。灯、颜色、线条与装饰参数均只绑定，不改。

新小地图保持三种数据含义：未知、已发现但当前不可见、当前可见；DebugRevealAll只在调试配置开启。当前原型是全图路径显示，这项是新增功能而非现状描述。
