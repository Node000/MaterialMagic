## 1. 核心结论：独立对象，同一套事实与结算

**参考 BuffModel，但不继承 BuffModel，也不把遗物变成不清除的 Buff。**

复用的模式：数据定义 + 工厂 + 独立效果子类 + 对象私有状态 + 明确规则钩子 + UI 读取显示。不同点：

| 对象 | 所属与生命周期 | 负责什么 |
| --- | --- | --- |
| BuffModel | 玩家或敌人的战斗状态容器，遵循既有清理/衰减 | 层数、临时规则、状态间反馈 |
| RelicModel | 玩家本局的独立库存，跨节点/战斗/场景 | 遗物条件、计数、充能、主动派生效果 |
| PlayerState / EnemyModel / BattleManager | 既有规则对象 | 生命、护盾、牌堆、行动、受击、死亡与阶段的真实提交 |
| 新增的窄结算桥 | 依附当前玩家/战斗，不是第二套世界状态 | 来源上下文、遗物分发、派生效果与实际结果记录 |

交互依赖如下：

```text
玩家操作 / 道具 / 敌人 / Buff / 遗物
                ↓ 调用同一规则入口
生命、护盾、Buff、抽牌、箭头读取等实际提交
                ↓ 带来源的事实结果
         Buff 原有反馈 + 遗物钩子
                ↓ 产生新请求
         再进入相同规则入口
```

遗物可以读取玩家/敌人的基础信息，也可以修改下一次结算请求；但不能直接写生命、护盾、Buff 字典、牌堆列表或其他遗物的私有计数。两个遗物通过“产生效果 → 观察实际结果”配合，而不是互相按 ID 调方法。特殊内容若确有直接充能需求，再增加有类型的库存命令，不暴露可写集合。

## 2. 已核对的现有代码与风险

| 当前入口 | 已确认行为 | 本设计必须处理的点 |
| --- | --- | --- |
| `Assets/Scripts/Data/BuffModel.cs` | 虚方法钩子、工厂、层数；CombatantModel 桥接玩家/敌人 | 复用 CombatantModel，不再建立第三套战斗单位包装 |
| `Assets/Scripts/Data/PlayerState.cs` | Buff、生命、护盾、金币、牌堆；各类 Trigger 方法 | 实际提交点在这里，不只在 UI 或 BattleManager 发事件 |
| `Assets/Scripts/Data/EnemyModel.cs` | 受击、Buff、意图、死亡排队 | 玩家遗物也应观察敌人身上的实际变化，不能只扩展玩家 Buff 容器 |
| `Assets/Scripts/Data/PlayerStatus.cs` | 继承 PlayerState，增加局内随机 seed/step | 遗物库存放 PlayerState 即可被 PlayerStatus 持有，不能两处各维护一份 |
| `Assets/Scripts/Data/MagicModel.cs` | 每次重放均执行施法钩子；攻击辅助函数包含强化、攻击 Buff、受击、后置反馈 | 施法次数、攻击次数、命中次数不能混用；不能靠 UI 连击数统计遗物 |
| `Assets/Scripts/Data/BattleManager.cs` | 阶段入口、目标、死亡队列；FinishBattleRules 清战斗状态 | 遗物实例不随 ClearCombatState 清空；战斗结果钩子需带胜负 |
| `Assets/Scripts/HandSystemUI.cs` | 箭头基础效果、读牌/施法协程、玩家交互和节点编排仍在此 | 只把相关规则切点接入桥，不在本次设计中全量重写大 UI 类 |
| `Assets/Scripts/RunSaveSystem.cs` | 版本 3，节点快照，玩家持久状态和战斗快照分开 | 没有遗物 DTO、奖励领取状态；不能只加一个 relicIds 数组 |

特别注意：

1. Buff 施加链已有“来源 OnGiveBuff → 目标 OnReceiveBuff → 加入 → 来源 AfterGiveBuff”，且按 BuffEnum 排序；攻击等部分钩子是容器快照顺序，并非全部统一排序。首期保留旧 Buff 之间的相对顺序，不借遗物接入全局重排。
2. `SpellPowerOnExtraDrawBuffModel.OnReceiveBuff` 会直接新增 Buff；`ShieldReflectBuffModel.AfterTakeDamage` 会同步造成新伤害。现有 Before/On 钩子不是全部纯函数，不能贸然把整套 Buff 改为异步事件队列。
3. `TakeDirectDamage` 是跳过护盾及普通受击链的直接扣血；“遗物直接造成伤害”不代表应该默认调用它。
4. `AfterAttack(ref attackResult)` 可改返回/表现数值，但不能反向改变已扣生命；新遗物统计必须读实际 CombatDamageResult，不读被改过的 attackResult。
5. `DrawCardsForRefresh` 不走普通 AfterDraw；回手和临时入手也不等于抽牌。入手/抽牌/换牌必须区分。
6. 部分 Buff 直接写 `stack = 0`、HalveStack 或 AddStack；现有 BuffAdded 事件只覆盖添加，而且同时用于表现，不能拿它充当完整的规则事件总线。
7. `SaveRunProgressForce` 已存在，但不等于快照已能保存奖励流程；ExportCurrentNode 没有遗物候选或领奖阶段。PlayerCombatSaveData 目前没有完整玩家战斗 Buff 快照，常规 preparedBuffs 也不是所有战斗 Buff/私有状态的通用保存。

## 3. 类与文件划分（拟新增）

### 3.1 定义和工厂

沿用 GameDataReader / GameDataDatabase 的数据加载方式：

- `Assets/Scripts/Relics/RelicData.cs`：RelicData、RelicPoolData、必要的枚举与参数 DTO。
- `Assets/Resources/Data/RelicData.json`：稳定 numericId/string_id、本地化 key、图标资源标识、稀有度、script、效果参数、重复补偿。
- `Assets/Resources/Data/RelicPoolData.json`：按渠道的池、权重、候选数、价格规则引用、开放条件。
- `Assets/Scripts/Relics/RelicFactory.cs`：显式注册 script → 构造函数。未知 script 是内容错误，不能悄悄返回没有效果的 RelicModel；新发放应拒绝并记录错误，旧档按第 10 节保留。
- 每个遗物独立 `Assets/Scripts/Relics/具体名称RelicModel.cs`，方便像 Buff 一样单独维护与测试。

配置只读，所有计数存在实例。参数优先用小型有类型参数结构；不建设表达式脚本语言或万能条件树。数值、门槛、价格和补偿不散落在 UI 或效果代码。图标/布局/颜色遵循现有资源与序列化配置，禁止效果代码回写美术颜色。

### 3.2 RelicModel 与库存

```csharp
// 以下均为拟新增契约；事件 DTO 的字段见第 4 节。
public abstract class RelicModel
{
    public RelicData Data { get; }
    public string InstanceId { get; }
    public long AcquisitionOrder { get; }

    public virtual void OnAcquired(RelicContext context) { }
    public virtual void OnBattleStarted(RelicContext context) { }
    public virtual void OnPlayerTurnPreparing(RelicContext context) { }
    public virtual void AfterCardDrawn(RelicContext context, CardDrawnEvent value) { }
    public virtual void AfterArrowRead(RelicContext context, ArrowReadEvent value) { }
    public virtual void BeforeDamage(RelicQueryContext context, DamageRequest value) { }
    public virtual void AfterDamageResolved(RelicContext context, DamageResolvedEvent value) { }
    public virtual void BeforeBuffApplied(RelicQueryContext context, BuffApplyRequest value) { }
    public virtual void AfterBuffApplied(RelicContext context, BuffAppliedEvent value) { }
    public virtual void AfterBuffChanged(RelicContext context, BuffChangedEvent value) { }
    public virtual void AfterMagicResolved(RelicContext context, MagicResolvedEvent value) { }
    public virtual void OnBattleEnded(RelicContext context, BattleEndedEvent value) { }

    public abstract RelicSaveData ExportState();
    public abstract void RestoreState(RelicSaveData value);
}
```

以上为代表性钩子，不要求子类全部重写。完整首期切点表见第 6 节。不要照搬 Buff 的单一 stack 为所有遗物状态：计数、充能和次数可同时存在，应由具体子类维护具名字段。

`RelicInventory` 由 PlayerState 持有，内部有获得顺序列表和 ID 查询索引：

- 公开只读 Relics；通过 `TryAcquireRelic` 唯一入口发放，返回 Acquired / DuplicateCompensated / Invalid / NotAvailable 等明确结果。
- 新局为空，跨战斗保留；销毁运行对象时解绑，不建立静态库存。
- `RelicsChanged` 表示增删；`RelicStateChanged` 表示计数/充能显示变化。两者是 UI 通知，不再次参与规则结算。
- RestoreState 仅恢复；不调用 OnAcquired，不重复给予护盾、金币或充能，不消耗随机步数。
- 每次遗物分发冻结列表，按 AcquisitionOrder 执行；执行前核对实例仍有效。同一轮新增的遗物不补收旧事件，但能响应此后产生的事件。

### 3.3 上下文、分发与效果入口

| 拟新增对象 | 责任 |
| --- | --- |
| RelicContext | 当前拥有者、可空的 BattleManager、节点上下文、效果入口、当前触发信息；不引用 UI |
| RelicQueryContext | 只读查询、预览/正式求值信息；不提供施加效果或写计数的方法 |
| RelicDispatcher | 对该玩家的库存进行具名钩子分发、快照与顺序管理 |
| EffectResolutionScope | 一次顶层规则操作的临时上下文栈、事件序号、遗物派生请求队列和结果批次 |
| CombatEffectResolver | 封装伤害/Buff/护盾等请求，并委托现有实际提交入口；不是第二套生命计算器 |
| RelicEffectActions | 遗物可调用的窄门面：施加 Buff、伤害、护盾、治疗、抽牌、金币等 |

库存/分发/局外效果门面与 PlayerState 同生命周期；战斗开始时绑定对应 BattleManager，结束后解除。测试用 `new PlayerState(...)` 同样可用，无需存在 RunManager.Current。EnemyModel 不查全局库存；由所属结算 scope/绑定战斗提供分发对象。局外节点允许 BattleManager 为空，战斗专用命令在该状态明确拒绝。

不向 UnitModel、CombatantModel 增加一份遗物集合，不增加 MonoBehaviour 单例。复用既有单位接口和战斗对象，避免一份状态多个来源。

## 4. 三种协议：修正请求、提交事实、派生效果

### 4.1 修正请求：决定“这次要发生什么”

Before/Modify 接口只修改当前请求的可写数值或许可结果，不得改变计数、随机状态、生命、Buff 和库存。

- DamageRequest：来源、目标、基础值、工作伤害值、伤害策略、攻击/施法/段数标识。
- BuffApplyRequest：来源、目标、BuffEnum、请求层数、工作层数。
- ShieldGainRequest / GoldGainRequest / HealRequest：请求值、工作值、来源及明确原因。

一次性增伤/减伤的可用次数，只在正式提交结果阶段消耗；若有多段攻击，上一段提交后，下一段自然读取新次数。不能在求值阶段直接递减，也不能把随机抽取放进 Before 钩子。首期数值修正尽量只采用确定性规则；确需随机时由正式结算先生成可复用的决定，再参与计算。

旧 Buff 钩子继续在原时点同步执行；**不要求旧 Buff 在首期全部改成纯查询**。新增遗物的 Before 接口必须是纯的，避免扩大旧的副作用问题。

### 4.2 事实事件：说明“实际发生了什么”

事件是提交后的只读快照，不是可改的请求，不把可变 CombatDamageResult 原引用直接暴露给遗物。

每个事件共有：RootActionId、EventId、ParentEventId、EffectOrigin、阶段/战斗/回合标识。按类型另有：

| 事件 | 必要字段 |
| --- | --- |
| DamageResolvedEvent | 来源单位、目标单位、策略、Raw/Final/Shield/HealthDamage、是否从存活变死亡、AttackId/CastId/HitIndex |
| BuffAppliedEvent | 来源、目标、类型、请求量、修正后请求量、实际前后值、是否新增/覆盖/未改变 |
| BuffChangedEvent | 目标、类型、Before/After、ChangeReason、可知时的来源；包括添加、消耗、衰减、过期、清理 |
| CardDrawnEvent | 真实牌 instanceId、DrawReason、本次实际入手结果、DrawBatchId |
| CardEnteredHandEvent | 牌、FromZone、EnterReason；不自动重复算作抽牌 |
| ArrowReadEvent | 源牌 instanceId、实际步骤、是否重读、读取/重复索引、方向列表；在真正结算处产生 |
| MagicResolvedEvent | 道具 ID、CastId、RepeatIndex、本次结果；不把箭头基础伤害算作施法 |
| GoldChangedEvent | 请求值、实际变化、原因、是否正常收益/退款/初始化 |
| BattleEndedEvent / NodeCompletedEvent | 胜负/节点类型、唯一完成标识、奖励阶段；不是面板关闭回调 |

实际护盾获得为 0、抽牌失败、Buff 被挡到 0，都不能伪装成“成功获得”。若遗物需要“尝试”语义，另用请求完成事件/Applied=false 字段，不让所有获得类钩子都误计数。BuffChanged 中的清理可以被观察，但默认内容过滤 BattleCleanup/Restore，防止战后清空触发攻击或奖励。

### 4.3 来源：归属者不等于攻击性质

`EffectOrigin` 分开保存：

- **Owner/SourceUnit**：归属哪个单位，用于 Buff 来源链、反击目标和击杀归属；可空。
- **Kind + DefinitionId + InstanceId**：Magic / ArrowBase / Buff / Relic / EnemyIntent / Event / System 等。
- **RootActionId、ParentEventId、TriggerPath**：这次效果从哪条行为链派生。
- **AttackId、CastId、牌实例、RepeatIndex**：仅对应操作存在时填，不硬造。

由玩家遗物直接施加的 Buff，SourceUnit 为玩家，因此能自然经过玩家 OnGiveBuff、目标 OnReceiveBuff、AfterGiveBuff，例如泡沫板的反馈；Origin.Kind 仍是 Relic。不能为了避免攻击增伤而把来源设成 null，也不能为了展示来源而把它冒充 Magic。

现有聚合 Buff 同类型只有一个对象，不保存每一层的施加者。首期不承诺逐层来源追踪：已有 Buff 后续燃烧的来源按 Buff 结算策略记录，不能把混合后的所有燃烧伤害都算成最后一个遗物的伤害。精确逐层归属若成为内容需求，应另立迁移，不在遗物接入时暗改 Buff 数据结构。

## 5. 数值结算的具体契约

### 5.1 伤害分为三类

| 策略 | 进攻方 OnAttack / AfterAttack | 目标普通受击链与护盾 | 用途 |
| --- | --- | --- | --- |
| Attack | 是 | 是 | 道具攻击、上箭头基础攻击；明确写“进行攻击”的遗物 |
| EffectDamage（遗物伤害默认） | 否 | 是 | 遗物造成普通伤害；不会默认吃攻击力/虚弱，不触发“攻击后”Buff |
| HealthLoss | 否 | 否 | 明确写“失去生命/无视护盾”的效果；沿用直接扣血的基础语义 |

三类均可产出真实结果事件并进入死亡处理，但不同的内容钩子必须按策略过滤。EffectDamage 默认仍会经过目标易损等受击修正，击中护盾可触发护盾反射；内容若要忽略某类受击 Buff，要显式策略配置，不能靠删来源实现。

建议攻击链（旧步骤相对顺序不变）：

1. 建立原始请求，冻结本次目标与来源；AoE 固定初始目标列表，每一击执行前复核存活。
2. Attack 才执行既有道具强化 BeforeAttack（若确属道具）、来源 Buff OnAttack；随后来源遗物的攻击值修正。
3. 目标 Buff OnTakeDamage；随后玩家遗物的目标受伤修正。通用遗物 BeforeDamage 按事件角色分发一次，不因玩家既是来源又是目标而重复分发。
4. 按策略扣护盾/生命，记录实际结果。
5. 执行现有目标 AfterTakeDamage 和死亡排队，再执行既有来源 AfterAttack/道具强化 AfterAttack。旧同步嵌套效果保持原行为。
6. 发布本击不可变 DamageResolvedEvent；遗物按实际 HealthDamage/ShieldDamage 等更新状态并排队派生效果。
7. 排空本原子操作的遗物派生队列，再进入下一击/下一次抽牌/下一个道具。死亡规则和表现接既有死亡管线，不能直接 Destroy 敌人或提前发战斗胜利。

HealthLoss 另有清晰的生命损失事件，不补调旧 AfterTakeDamage，否则燃烧等现有行为会发生变化。“受伤反击”默认只认普通受击的 HealthDamage > 0，是否响应自损由具体内容显式声明。

遗物增伤/减伤相对旧 Buff 的位置是新增规则。若将来需要“翻倍后加值”等多阶段公式，必须显式增加阶段，不能靠任意 priority 数字或类名排序解决。

### 5.2 Buff 施加和变化

拟接入顺序：

```text
来源 Buff OnGiveBuff
→ 来源遗物 ModifyOutgoingBuff
→ 目标 Buff OnReceiveBuff
→ 目标遗物 ModifyIncomingBuff
→ 沿用具体 Buff 的合并/覆盖/拒绝规则
→ 提交 BuffAdded 表现通知、来源 Buff AfterGiveBuff
→ BuffApplied / BuffChanged 事实
→ 遗物派生队列
```

来源或目标涉及玩家时才执行对应玩家遗物修正；全场 BuffApplied 观察每个事件只分发一次，事件带角色让遗物自行筛选。自我施加可以经过出/入两个**不同阶段**，但提交事实不重复。

- 保留 AttributeDisabled 覆盖方向、DoubleEnemyBurningOnTurnEnd 不叠加等特殊规则。AppliedStack 不能一律等于 stackAfter-stackBefore；覆盖型数值不是普通层数增量，DTO 必须带 ApplyMode。
- 添加结果事件放在旧 AfterGiveBuff 之后，但携带提交瞬间的前后值，防止该回调又改同一 Buff 使数据失真。
- 新增遗物需要的层数变化切点，不能仅监听 BuffAdded。首期在 AddBuff/ConsumeBuff、ClearBuffs、Buff 钩子执行和过期移除边界记录变化，统一由一个变化记录器发布。
- 对旧 Buff 直接改 stack 的兼容：围绕最内层 Buff 钩子调用记录进入/退出值，嵌套变化记录由同一记录器登记并扣除，外层只报告未被子记录覆盖的变化；不得“父调用末尾再比较整个字典”而重复报子调用。钩子内多次无通知的裸写只承诺观察净变化。
- 新代码不得裸写其他对象的 stack，后续逐步让 SetStack/HalveStack/ConsumeStack 使用统一通知入口。若内容需要观察同一次钩子内每次加减，必须先迁移该 Buff 的裸写，再声称精确支持。
- Buff 快照继续遵守既有规则；遗物在事实之后新增的 Buff 不追溯影响本次已提交请求，但可以影响下一次效果。这样避免“新状态倒改刚刚结算的伤害”。

### 5.3 护盾、金币、治疗

- 护盾：既有非迟缓 Buff 修正 → 遗物修正 → 迟缓最后削减 → 提交 → 消耗迟缓 → 实际获得事件。必须保持现有迟缓实际消耗规则，不能在预览时消耗。
- 金币：正常正收益先按现有进阶修正，再遗物收益修正，最后提交；支出、初始化、读档、退款不吃收益加成。新增明确 GoldChangeReason，不能只凭 amount > 0 判断退款是奖励。
- 治疗：实际治疗量受生命上限夹取后再记事件；复活另立规则，不能用普通 Heal 在死亡后隐式复活。派生治疗执行前复核拥有者存活。
- 新遗物默认不能在玩家已死后继续进攻/治疗；死亡触发型遗物需显式允许。首期不支持“免死/复活”而不明确死亡提交窗口。

## 6. 生命周期与玩家操作计数

### 6.1 战斗与回合

| 拟新增钩子 | 放置位置 / 语义 |
| --- | --- |
| OnBattleStarted | 战斗对象/敌人/关卡绑定完成后，旧 TriggerMagicBattleStart 后、首回合前；仅新战斗一次 |
| OnPlayerTurnReset | 玩家每回合标识递增后，先重置本回合遗物预算；不产生效果 |
| OnPlayerTurnPreparing | 旧护盾清理和 Buff OnTurnStart、箭头强化回合开始之后，正常抽牌前 |
| AfterPlayerTurnDraw | 正常回合抽牌及其派生完成后，带真实抽牌批次；保留旧 AfterTurnStartDraw 的语义 |
| AfterPlayerTurnStarted | 旧 AfterTurnStart 和道具 TurnStart 后，交互开放前 |
| BeforePlayerTurnEnd | 旧玩家 OnTurnEnd 前，用于读取尚未清理的状态 |
| AfterPlayerTurnEnded | 旧 EndPlayerTurnRules 的状态清理后 |
| Before/AfterEnemyAction | 既有单敌人行动入口两侧，不替换逐击结算；敌方整轮和单个敌人行动不可混用 |
| OnBattleEnded | 死亡规则队列与派生效果稳定，胜负已确定、清 Buff 前一次；显式胜利/失败 |
| OnBattleCleanup | 只清遗物 Battle/Turn 临时状态，不产生战斗效果；实例与 Run 计数保留 |

“战斗开始护盾”若在首回合清盾前给予，会立刻丢失。因此此类遗物在 OnBattleStarted 标记待发，在首个 OnPlayerTurnPreparing 真正 GainShield，或使用专门的首回合准备钩子；不能假设 BattleStarted 已经等于首回合准备完成。

读档已有战斗快照时只重建绑定和恢复状态，不重播 BattleStarted/TurnReset/OnAcquired。需要 UI 刷新可以发独立的 Bound/Restored 通知，不复用规则生命周期。

### 6.2 卡牌操作：把“布置”与“使用”分开

| 事实 | 默认计数语义 | 实际接入位置 |
| --- | --- | --- |
| 成功从手牌放入出牌区 | 布置，不默认给不可逆收益 | PlayerState.TryMoveHandCardToPlay 成功后，显式 Player/Effect/Event 原因 |
| 撤回出牌 | 与布置对应，退额度；不能算弃牌或再抽牌 | TryMovePlayCardToHand 后，保留旧 Buff 行为但新增事实标明 Return |
| 实际读取一个箭头步骤 | 默认“使用箭头”计数；重读是否计入由遗物配置 | HandSystemUI.ResolveArrowReadStepEffect 的实际执行点 |
| 消耗一张实体箭头 | 每张真正进入 ConsumedPile 一次 | AddConsumedCard 成功后；现有 MaterialConsumed/ArrowConsumed 两钩子不能让遗物重复计数 |
| 匹配并施放道具 | 每次实际施放一次，包括重放实例 | MagicModel.Cast 循环内部；不是 HandSystemUI.RegisterMagicCast |
| 命中/受伤 | 每个目标、每一击一条实际结果 | 伤害提交点；AoE 命中数与攻击次数另有 AttackId |
| 抽牌 | 真实 DrawReason 的成功抽牌；不包括换牌补充和回手 | DrawCardToHand / 对应实际入手入口 |
| 换牌 | 成功完成的一次操作和实际替换结果 | RefreshCombatCards 等规则入口；不监听拖拽回调 |

默认不提供“反复放入/撤回就无限计数”的奖励遗物。确需根据布置操作充能时必须设计去重（回合+牌实例）或提交/撤销机制。失败拖拽、超限、被禁用、同区排序、效果入区、事件选择都不应误算主动打牌。

ArrowReadSystem.BuildSequence 在事件选择等路径也被调用；不能在构建序列时增加遗物计数，必须在实际读取执行处触发。重读次数、基础效果重复次数、Token 数量和实体牌消耗数量分别记录，内容不能含糊使用一个 OnPlayCard。

## 7. 顺序、嵌套和防止无限触发

### 7.1 最小调度策略

- 旧 Buff 的同步副作用与现有相对顺序保留；新增遗物派生效果通过 `context.Actions` 排队，不在库存遍历中直接递归调用结算。
- 一次原子操作定义为：一击伤害（含旧后置链）、一次 Buff 施加（含旧 AfterGiveBuff）、一张牌成功抽取、一个读取步骤或一个生命周期回调批次。
- 事实按真实提交序号存入 scope；本原子操作旧规则链返回后，按提交顺序分发事实，同一事实内按获得顺序执行遗物。
- 遗物回调可以同步改自己的计数并标脏 UI，但派生效果 FIFO 排队；本批事实分发完后执行队列，新的结果追加到队尾。多段攻击下一击前必须排空，才能让新护盾/易损/次数真实影响下一击。
- 若旧 Buff 在调用栈中产生嵌套伤害，沿用旧行为；新遗物响应要等当前旧原子链安全返回。提交序号在数值落地时分配，因此外层事实先于其后置回调产生的嵌套事实。
- 动画、声音、浮字不决定队列执行进度。规则完成后输出本批次结果，再由 UI 依顺序表现。

需要在 Begin/EndPlayerTurnRules、逐敌人逐击、MagicModel 攻击辅助与基础箭头切点明确 scope 边界，而不是用一个覆盖整场战斗的大队列。跨帧协程不持有静态 CurrentContext；短同步作用域用 try/finally 栈恢复，避免嵌套把上一层上下文清成 null。

### 7.2 三层防环

1. 每个事件有独立 EventId，单个遗物对同一事件至多处理一次。
2. 派生链携带 `(RelicInstanceId, HookKind)` 路径；默认同一路径不得重复进入同一遗物同一钩子，阻断 A→A 与 A→B→A。同一玩家操作产生的两次独立命中不是同一路径，不因此吞掉正常触发。
3. 具体遗物明确 Origin 过滤、每回合预算和触发条件；另有每根操作的派生请求总量上限，只作为程序错误保险。达到上限输出完整路径诊断并让本次结算失败可见，不静默跳过后继续保存“半个结果”。

首期不允许内容任意关掉防环。需要“遗物触发遗物”是允许不同钩子/不同路径的正常反馈，不等于允许循环自激。旧 Buff 之间的既有同步无限递归不因新增队列自动解决；若新内容触及这类链，需补充对应规则防护和测试。

## 8. 预览、状态和实例计数

### 8.1 预览不许推进任何状态

现有 EnemyModel.GetIntentAttackValue 会调用攻击/受击的数值钩子，护盾预览也调用 OnGainShield。新增遗物不能直接挂入这些通用 Trigger 方法而不区分预览。

- 正式提交和预览使用相同的确定性数值公式，但预览上下文不提供命令、计数提交、随机抽取与通知。
- 多段预览在只读投影的临时副本上模拟易损衰减、一次性减伤预算等，不只拿第一段数值乘段数，也不改真实状态。
- 旧 Buff 前置钩子若存在副作用，不允许对真实对象调用后再“撤销”；使用专用纯查询/完整隔离投影。第一批只支持经过验证的预览公式，不为未知复杂反击连锁伪造精确总值；UI 可显示基础攻击预测并明确其不包含连锁效果。
- 这是数值修正型遗物上线前置项，不是所有遗物做完以后才补。反复悬停、刷新敌人意图不得吃次数、充能或 RNG step。

### 8.2 状态分层

| 范围 | 例子 | 重置点 |
| --- | --- | --- |
| RunState | 本局累计读取数、跨战斗充能 | 新局/明确消耗 |
| BattleState | 本场首次施法已用、待发开局护盾 | 新战斗/战斗清理 |
| TurnState | 本回合是否额外抽牌、反击次数 | 新玩家回合正式开始 |

计数变化先提交再排队效果。例如“每读取 N 次，造成伤害”：先扣除阈值/写入余数，再排队伤害，避免伤害引发的新事件重复看到旧计数。是否单次跨越多个阈值要由内容契约规定。

默认次数按**成功承诺触发**消耗：例如首次施法在真实 CastStarted 提交时消耗（即使该法术没有命中）；伤害型充能必须先有合法目标，才消费并排队。执行时目标已死亡，默认取消且不临时随机改目标；是否返还充能需定义为内容策略，不能失败后自动重试刷收益。

## 9. 典型交互走查（机制示例，不是数值定案）

### A. 遗物给敌人 Buff，Buff 再改变基础信息

回合准备 → 遗物对敌人施加燃烧 → 来源填玩家 → 玩家 OnGiveBuff 增幅 → 敌人 OnReceiveBuff → 实际加入 → 玩家泡沫板 AfterGiveBuff 获得护盾 → 护盾结算经过防御力/迟缓 → 遗物收到真实 Buff/护盾结果。

结论：无需遗物代码专门识别泡沫板，互通来自共同入口和正确来源。

### B. 玩家使用箭头，遗物计数，遗物直接伤害

实际读取步骤 → 累计读取次数 → 达阈值先记余数 → 选择并冻结合法目标 → 排队 EffectDamage → 经过目标易损和护盾 → 受击 Buff 反馈 → 死亡排队 → 发实际伤害事件 → 其他遗物可响应。

结论：不会触发“施法后电弧”，也不会默认消耗玩家虚弱；不是 TakeDirectDamage 绕过防御。若内容明确为攻击，则显式使用 Attack 策略。

### C. 受伤反击与护盾反射共存

敌人逐击攻击 → 提交玩家真实护盾/生命损失 → 原护盾反射同步完成 → 遗物按 HealthDamage > 0 更新次数并排队反击 → 执行前复核玩家和攻击者存活 → 反击产生新的受击结果。攻击者已被原护盾反射击杀时，不能再对死者扣血；不能在死亡演出结束前让下一个敌人规则越过。

### D. 首抽额外抽牌

成功普通抽牌 → 遗物先置本回合已触发 → 排队额外抽牌，原因 RelicBonus → 新抽牌仍有真实 Drawn 事件，但该遗物已用完次数且路径防环阻止自激。换牌入手不触发“首抽”。手牌已满时无成功抽牌事件，不消耗首抽资格；若首抽已成功但奖励抽牌被手牌上限挡住，资格不返还。

### E. Buff 变化影响遗物计数

目标燃烧实际衰减/消耗 → BuffChanged 携带 Before/After/Reason → 遗物只筛选真实消耗或衰减、排除 Restore/BattleCleanup → 累积净减少量 → 达阈值给予 ExtraDraw Buff → 既有 SpellPowerOnExtraDraw Buff 再给予法强。

结论：不要求 Buff 持有具体遗物引用；观察实际变化即可。若同一个 Buff 钩子内部先加后减且净值为零，兼容层不保证记录中间步骤，内容要支持这种精度必须先迁移该钩子的状态写入。

## 10. 二层开放、获得和存档

### 10.1 开放门控

- 新增可保存的楼层/成长门控状态，由 RunManager 的正式进入楼层流程更新；不能只读统计埋点 RunAnalyticsLedger 的楼层，也不靠场景名包含 SecondFloor 判定。
- `HandSystemUI.EnterSecondFloor` 目前有接口但未接常规流程。正式接入时在地图生成成功后、切场景前提交门控及快照；失败不提前开放。教程默认关闭。
- 所有精英奖励、事件 GainRelic、商店生成共用 `CanOfferRelics` 检查；TryAcquireRelic 也检查上下文，防止一层事件绕过门控。测试/调试明确传 bypass，不污染正常规则。
- 门控主要限制首次开放/投放。已持有遗物的效果不因界面隐藏、切场景或缺少商店面板失效。
- 首次进入二层是否必送一个遗物、是否立即三选一、具体池与稀有度是内容决策，不能由工程默认“顺手送一个”。

### 10.2 发放与交易

- 默认无容量上限、唯一持有。候选先排除已持有；候选不足允许减少数量，是否用重复候选补齐为池配置，不能用无限重抽。
- 重复领取按遗物配置补偿，金币原因标为 DuplicateRelicCompensation；是否吃金币遗物加成由收益策略明确，默认不吃以免反复转换获利。
- 遗物商品直接提交，无道具槽替换/撤销购买。商店遗物价格、购买标记与库存变更须同一份快照提交；不能扣钱成功后物品保存失败。
- UI 点击只请求领取；库存修改、补偿、候选已领取标记和后续流程推进由规则结果决定。按钮连点必须由 Pending/Committed 状态阻断。

### 10.3 保存结构

拟新增 `RelicSaveData`：numericId、InstanceId、AcquisitionOrder、stateVersion、Run/Battle/Turn 状态数据。每类状态采用该遗物定义的有类型 DTO，允许用现有 Newtonsoft 做显式版本化负载，但只按工厂白名单恢复，禁止保存 CLR 类型名并任意反射构造。

- PlayerSaveData 保存遗物实例数组和开放状态所需数据；RunSaveData / RunManager 保存权威楼层上下文。Battle/Turn 状态只有与同一战斗快照一起恢复才有意义，不能把战斗临时状态单独混到另一场战斗。
- CurrentNodeSaveData 扩展奖励流程 DTO：候选 ID、领取阶段、已选项、是否已提交、战斗结算/节点完成标记。
- ShopOfferSaveData 追加 Relic 类型与 ID，保留旧 kind 数值，不重排已有枚举；EventEffectData 扩展 relicId/relicPoolId，实际实现 GainRelic case。
- RunSaveSystem 当前版本为 3，实施时新增版本迁移；旧档无遗物集合视为空。旧二层档门控仅通过受控迁移推导一次并保存，不在每帧猜测。
- 未知遗物 ID/未知状态版本保留原 DTO 为禁用占位，记录一次诊断；不调用未知效果、不丢原数据、不在读档时自动补偿金币。内容修复后可恢复。
- 同一个快照保存随机 seed/step、固定候选、商品购买状态及遗物状态；读档不再次随机候选。

### 10.4 提交边界：不能只靠强制保存

先支持稳定边界保存：遗物领取、购买、事件效果完成、楼层进入及安全战斗检查点。scope 还有派生请求/事实未分发、死亡规则未收口时不能导出混合快照。

- 遗物获奖必须在库存、候选领取标记、节点阶段一起更新后强制保存；写盘失败不推进/切场景，保留同一事务等待重试，不重新发放和重掷。
- 不为每个遗物计数变化立即写盘。战斗计数随整个安全检查点共同保存；暂停发生在结算中时保存最近完成的检查点，不能只落遗物计数而回滚生命/牌堆。
- 首期可承诺“恢复到最近稳定检查点”，不能承诺任意动画中逐帧恢复。奖励已提交但 UI 还没播完时，恢复后只补界面，不再领奖。
- 玩家完整战斗 Buff 及其有状态子类需要与安全战斗快照一致。至少保存所有影响遗物联动的状态；仅保存 BuffEnum+stack 不足以恢复 ExtraDrawOnEnemyDamage 等私有计数。若暂不做通用 Buff 私有状态迁移，就限定可保存点为没有这类未保存状态的边界，并明确恢复粒度，不能只保存遗物就宣称精确恢复。
- 一并避免普通保存把二层 sceneName 写回 null；楼层门控、场景路由和当前节点应来自同一权威运行状态。

## 11. UI 和表现边界

拟新增 RelicBarUI、RelicView、RelicSelectionPanelUI 和对应 Tooltip 控件：

- 面板、顶部栏容器、Tooltip 直接在目标 Scene 搭建；只将遗物内容项做 Prefab 动态实例化。
- 使用 Inspector 显式绑定库存栏、面板、图标和配置，不按名称/路径查找场景节点。
- 控件只展示名称、图标、描述、计数/充能并发送领取请求；不能在 Refresh/OnEnable/悬停时结算遗物。
- RelicEffectResultBatch 记录实际命中、治疗、护盾和触发实例，交给 HandSystemUI / 对应 presenter 表现；不伪造 MagicCast 来借用特效和计数。
- 接既有敌人死亡队列和表现屏障，结果批次注明唯一消费标识，避免既有伤害浮字与新增遗物结果双播。
- PC/PE/二层场景逐一核对与绑定；不整体复制覆盖美术调参。本轮不创建这些对象。

## 12. 推荐实施顺序与完成标准

### 阶段 A：状态骨架与开放状态

数据/工厂、库存与状态 DTO、二层门控、迁移和纯恢复。先用测试注入库存，不依赖 UI。

完成标准：新局/旧档/未知 ID 可控；跨战斗保留；恢复不重复 OnAcquired、不推进 RNG。

### 阶段 B：规则桥与事件事实

明确 scope、来源和派生队列；接伤害、Buff 施加/变化、护盾、抽牌/读取、施法、生命周期。先不接商店和精英 UI。

完成标准：无遗物时原规则不变；下表的 Buff 双向联动、预览、防环和死亡测试通过；数值型遗物上线前完成对应纯预览。

### 阶段 C：代表性遗物验证

至少覆盖：首回合护盾、读取计数伤害、施加 Buff、实际受伤反击、首抽额外牌、金币收益修正。它们是结构测试样例，不先锁定正式 ID/数值/稀有度。

完成标准：不同生命周期、来源策略、同一次操作多目标与多个遗物顺序全部可解释。

### 阶段 D：投放、场景 UI 和安全保存

GainRelic、精英奖励、商店、库存栏、Tooltip、奖励阶段保存、二层正式入口。逐渠道验证禁用门控和事务幂等。

完成标准：一层不投放，二层正常领取；连点/读档不复制；退出恢复候选、价格、购买与计数一致；PC/PE 实际点击可达。
