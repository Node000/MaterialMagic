# 道具触发顺序修复（同一起点匹配多个道具）

测试反馈：以某个箭头为起点可以匹配多组道具时，没有按道具栏布局从左到右触发，而是按配方长度从长到短触发。
实例：有害电波（3 格：风+水+土）与雪球（2 格：风+水）同时可触发时，先触发有害电波，即使雪球在道具栏左侧。

## 设计依据

- `Assets/Docs/教程文本与顺序审阅.md` 7-2：“以同一个箭头为起点，若满足多个道具的要求，则会按从左到右的顺序依次触发道具效果。”
- `Assets/Scripts/Data/PlayerState.cs`：`slotIndex` 即从左到右的触发顺序（`SetMagicAtSlot` / `RearrangeMagicSlotsByVisualOrder` / `NormalizeMagicSlots` 的注释与实现）。

## 根因

战斗结算里唯一决定“同一起点多道具”顺序的地方是 `Assets/Scripts/HandSystemUI.cs` 的收集函数（旧名 `CollectCastableMagicsByRecipeLength`）：

- 它遍历 `magicViews` 收集从当前 Token 起点能匹配的道具后，**按配方长度从长到短插入** `castableMagicViews`。
- 结算循环随后严格按 `castableMagicViews` 顺序施法，没有任何位置会再按道具栏顺序重排。
- 所以“长配方先触发”是这个排序的唯一来源：只要它还按长度排序，无论怎么调整视图顺序都不会生效。

## 修改内容

- 新增 `Assets/Scripts/MagicMatchOrderUtility.cs`：唯一的顺序规则入口 `CollectMatchedMagicIndices(magicsInLayoutOrder, tokens, startIndex, matchedIndices)`，按 `MagicModel.SlotIndex` 升序（道具栏从左到右）输出匹配下标，与配方长度无关；`SlotIndex` 无效时退回传入顺序兜底。
- `HandSystemUI`：`CollectCastableMagicsByRecipeLength` → `CollectCastableMagicsInLayoutOrder`，收集阶段就改用上面的工具类；新增两个复用缓存（`magicMatchCandidates` / `matchedMagicIndices`）避免结算循环内反复分配。
- `GetRecipeLength()` 保留，但现在只用于取匹配长度驱动线框/高亮（`matchLength`），不再参与排序。
- 新增回归测试 `Assets/Tests/Editor/MagicMatchOrderTests.cs`（5 例）：左侧短配方必须优先、按 `SlotIndex` 排序、`AnyTwoDifferentElements` 规则不插队、只收集从指定起点匹配的道具、无匹配时清空上次结果。

## 验证

- NUnit 用例：`MagicMatchOrderTests` 5/5 通过，`ArrowReadSystemTests` 3/3 通过（本工程 `com.unity.test-framework` 为 1.1.33，低于 Locus 测试工具的 1.4.0 门槛，因此以直接调用测试方法的方式在 Editor 内执行）。
- `SampleScene_PC` Play Mode 实机 A/B（Debug 战斗，箭头 风+水+土，两个道具分别放左右槽位）：

  | 道具栏布局 | 实际触发顺序（`[GameData] Resolve magic from arrow tokens`） |
  | --- | --- |
  | slot0=雪球(2 格)、slot1=有害电波(3 格) | 雪球 → 有害电波 |
  | slot0=有害电波(3 格)、slot1=雪球(2 格) | 有害电波 → 雪球 |

  两种布局都跟随道具栏位置变化，说明顺序由布局决定，而不是配方长度。

## 复测建议

1. 普通战斗 / 教程战斗中，道具栏左侧放雪球、右侧放有害电波，打出一组「风、水、土」。
2. 确认先出现雪球的施法表现与日志 `magic=magic_poison_fog`，再是 `magic=magic_harmful_wave`。
3. 拖动两个道具交换位置后重复一次，确认顺序随之交换。

## 2026-09-17：改为「按行从上到下、行内从左到右」（视觉阅读顺序）

移动端 PE 的道具栏是 4 行 × N 列的网格（`GridLayoutGroup`：右上角起、纵向填充、固定 4 行），
原来的「slotIndex 升序」实际等于“先把右列从上到下走完，再走左列”，与玩家看到的阅读顺序不一致。
现改为按**视觉阅读顺序**：行从上到下，行内从左到右。

### 实现

- 新增 `Assets/Scripts/MagicBookVisualOrder.cs`：
  - `ComputeRanks(area, slotPositions, ranks)`：按容器**当前真实布局**算每个槽位的阅读序号。
    弧形道具栏（带 `MagicBookCurveLayout`，PC）是单行，槽位顺序即阅读顺序；
    网格道具栏（启用 `GridLayoutGroup`，PE）按实际 y 聚成行、行内按 x 升序；其它情况退回槽位顺序。
    **道具栏增减导致的行列变化会自动跟随**，不需要为每种槽位数写规则（≤4 槽时单列即从上到下；>4 槽时新列出现在左侧，行优先顺序自动变成“左列顶 → 右列顶 → 下一行”）。
  - `ComputeRank` 的纯位置版本 `ComputeRanksFromPositions` / `GroupRows` / `ComputeDropTargetIndex` 便于单元测试。
- `MagicMatchOrderUtility.CollectMatchedMagicIndices` 增加可选参数 `visualRanks`：
  排序键优先用视觉序号，未传时退回 `SlotIndex`（旧调用点与旧测试行为不变）。
- `HandSystemUI.CollectCastableMagicsInLayoutOrder`：每次结算收集前按当前槽位 `anchoredPosition` 现算视觉序号
  （复用 `magicSlotPositions` / `magicSlotVisualRanks` 两个缓存，不在结算循环里分配）。
- 拖拽落点同步改为行优先：`HandSystemUI.GetMagicBookDropPreviewIndex` → `MagicBookVisualOrder.ComputeDropTargetIndex`。
  原来只比较 x，在 2 列网格上拖到左列会被算成靠后的槽位；现在按“指针最近的行 + 行内 x 插位”定位。
  单行布局（弧形道具栏 / 单行网格）仍沿用原来的“按 x 从左到右”插入语义，PC 手感不变。

### 验证

- 单元测试 `Assets/Tests/Editor/MagicMatchOrderTests.cs`：**15/15 通过**（原 5 例 + 视觉顺序 6 例 + 拖拽落点 4 例）。
- PE 场景真实布局（`PlayerArea/Rightside/MagicBookArea`，8 槽）：
  实际位置 x=411.65（右列）/179.85（左列），y=-43.85/-164.75/-285.65/-406.55；
  `ranks = [1,3,5,7,0,2,4,6]`，触发顺序 `=[4,0,5,1,6,2,7,3]`（行优先：左上 → 右上 → 第二行…），与预期一致。
- 5 槽（右列 4 + 左列 1）等边界情况由单元用例覆盖。

### 复测建议（移动端）

1. PE 战斗里放 2 个以上道具，让它们能从同一个箭头起点同时匹配，确认按“左上→右上→下一行”的顺序触发。
2. 增减道具数量（1→8）后重复上面一步，确认顺序跟随当前行列布局。
3. 拖拽道具时确认预览落点与最终位置符合阅读顺序（尤其是左列与右列之间拖动）。
