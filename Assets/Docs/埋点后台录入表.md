# TapDB 埋点录入表 + 开发者后台操作清单

用途：把本方案的事件与属性录入 TapTap 开发者中心的数据分析（TapDB）后台，并按官方流程「**先登记、后开发、再校验**」执行。
对应方案：`plan/Tap埋点与玩家数据统计方案.md`（§5 事件总览 / §6 字段详表 / §3.2 命名规范）。
命名规范：事件名与自定义属性名均为小写 `snake_case`，**不带 `#`**（`#` 是 TapDB 预置事件/预置属性专用）；同一属性名的类型必须恒定。

**登记用的三个导入文件（已按 TapDB 批量导入格式填好，可直接上传）**：

| 文件 | 用途 | 上传位置 | 内容量 |
| --- | --- | --- | --- |
| `Assets/Docs/event.csv` | 事件表 | 配置 → 事件管理 → 批量导入 | 35 个自定义事件 |
| `Assets/Docs/eventProp.csv` | 事件属性表 | 元数据管理 → 事件属性 → 批量导入 | 135 个事件属性（已带与事件的绑定关系；2026-10-01 新增 `replayed`＝补发标记，**需重新导入或手动补登记这一条**） |
| `Assets/Docs/userProp.csv` | 用户属性表（设备属性，`table_type=2`） | 元数据管理 → 用户属性 → 批量导入 | 10 个设备属性 |

> 三个文件都已清掉官方模板里的示例行与说明文字，只留表头 + 我们的数据，可直接上传。生成脚本：`Library/Locus/tmp/tapdb_fill.py`（改字段后重跑即可重新生成，保证与本文一致）。

## 第零部分：TapDB 预置事件（自动上报，**不需要你登记**）

TapDB 自带下列预置事件，客户端初始化后自动上报。因此**本工程不再自定义重复登记生命周期事件**（这就是为什么没有 `session_*` / `login_*` 事件）：

| 预置事件 | 显示名 | 对本作的用途 |
| --- | --- | --- |
| `device_login` | App 启动 | 启动次数、设备维度留存（漏斗起点） |
| `play_game` | 用户游玩 | **游戏时长**（启动/唤醒触发，后台/退出时上报）→ 「低时长用户」的那个“时长” |
| `user_login` | 账号登录 | 账号登录记录（我们已接 TapTap 启动自动登录） |
| `disconnect` | 用户登出游戏 | 登出 |
| `exception_crash` / `exception_error` / `exception_module_start` | 崩溃 / 错误 / 启动 | 排查“低时长离开”是否由崩溃导致 |

与本作无关、也不需要管的预置事件：广告类（`#ad_revenue` / `#ad_show` / `ad_click`）、付费类（`charge` / `refund` / `#charge_sandbox`）、战令（`#battlepass_levelup`）、体力（`#consume_stamina`）、任务（`#daily_quest_finish` / `#operation_quest_finish`）、抽卡（`#gacha`）、聊天与好友（`#chat` / `#friend_add`）、PVP（`#pvp_complete`）。

> 补充：TapDB 还有 `#dungeon_complete`（玩家参与副本/关卡）、`#resource_income` / `#resource_consume`（资源获取/消耗）、`#equipment_levelup`（强化装备）等**业务预置事件**，它们有固定字段结构并会喂给后台自带的关卡/资源看板。默认方案是用我们自己的 `node_*` / `battle_*` / `magic_acquire` 事件，不依赖它们；如果你希望后台自带的关卡/资源看板也亮起来，需要先在后台看到它们对应的属性列表，我再把我们的数据按那个结构额外上报一份。

## 第三部分：属性表（= `Assets/Docs/eventProp.csv` + `Assets/Docs/userProp.csv`）

属性分两类，**不要混**：

- **设备属性（用户属性，`table_type=2`）**：筛选/分部维度，客户端用 `TapTapEvent.DeviceUpdate` 上报一次，不需要每个事件携带 → 见 `Assets/Docs/userProp.csv`（10 个）。
- **事件属性**：挂在具体事件上的对局数据 → 见 `Assets/Docs/eventProp.csv`（135 个，已带绑定关系）。其中 `replayed` 是技朮字段：为 true 表示该事件是上次启动未上报成功、本次补发的（`#ts` 为补发时刻）。

## 备注：上报时的字段约束（客户端侧规则）

1. 列表类字段（`magic_ids`、`deck_ids`、`enemy_ids`、`option_recipes` 等）用 `,` / `;` / `|` 编码为字符串；超出长度时截断并把 `truncated` 置为 `true`。
2. 文本类字段（`magic_name`、`enemy_names`、`error_message`）截断到 60 字符。
3. 同一属性名的类型恒定（只用 string / int / bool），不要混用。
4. **不上报**任何账号昵称、头像、手机号等个人信息；`user_id` / `open_id` 只用于账号维度聚合。
5. 若后台对属性数量或值长度有更严格限制，请把后台提示发我，我按限制调整编码方式后再更新本表。
